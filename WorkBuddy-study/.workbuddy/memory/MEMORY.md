### SaaS 中间件集群实际跑的东西（2026-09-04 截图识别）
- **有**：Nacos（`nacos-0/1/2`，StatefulSet 自建）、Kong 网关（`kong-gateway-kong-*`）、Redis 接入层（`mp-redis-proxy`/`mp-redis-lua`，`mp-`=中间件平台自建代理）、Squid 出网代理（`mp-squid-*`）、Loki 日志栈（`key1-loki-*`/`loki-distributed`/`filerator`）、Prometheus+node-exporter+kube-state-metrics、CFS/CBS CSI、GPU 节点。
- **集群内没有**：MySQL/PG、Kafka/RocketMQ/RabbitMQ 的 Pod → **数据库与 MQ 疑似云托管（集群外）**，未最终确认。
- ⚠️ 用户曾说"mysql/redis/nacos/kafka 没有这四个"——那是**在业务集群 ConfigMap 里 grep 没搜到**，不是真没有。判断组件是否存在，要看集群实际跑什么 Pod，不要只在配置文本里搜关键字。
- **风险比原估更高**：中间件集群 = 注册中心 + 网关 + Redis 接入层 + 日志栈，它挂了是服务发现、入口流量、可观测一起丢。
- **Kong 角色未定（关键）**：Ingress Controller 只能 watch 所在集群，集群内 Kong 通常管不到业务集群，除非是 TSE 云原生网关（托管版，跨集群关联服务来源）或多集群配置。可能是①中间件自用 ②平台级统一入口 ③另有托管版。**问清前不要假定它是业务入口。**

## 交付形式偏好

- **不要生成一次性 .sh 排查/摸底脚本**。用户 2026-09-03 明确说过「别脚本了，还是我自己一点一点找吧」。他要的是**一条一条敲、逐步看输出**的过程感与掌控感。
- 正确做法：在回复里按步骤给**可手敲的单条命令**，每条说明「看什么 / 怎么判断」，而不是打包成脚本文件让他跑。
- 例外：需要四环境 diff 时，可以给**一行 for 循环**（现场敲、当场看），但不要落成文件。

## 文档写作约定（重要）
- **严禁编造交付物**。用户多次澄清：没有学习笔记、没有配置梳理清单、没有服务梳理清单。写总结时，没产出的就写"进行中 / 熟悉中 / 认知层面，未形成对外文档"，不要虚构"产出笔记 N 份"。
- 同理，不要替用户编造"具体收获/结论"。不清楚的内容，退回到客观可验证的表述（学了什么、做到什么程度）。
- 用户明确要求：**工作总结不写个人想法、建议章节**。
- **不单设「未完成事项」章节**（已验证）：独立成章必然要写"计划完成时间"，而**组长从未给过 deadline**，写出来等于凭空给自己记一笔延期。正确做法：把"未完成事实 + 原因 + 预计时间"写进对应小节末尾的「当前状态 / 当前进展」（如 2.2、2.3），信息不丢且不造债。
- ⚠️ **不要写推导出来的"影响分析"列表**：我曾把"没有命令行发版"展开成"1 发布步骤沉淀不下来 2 配置差异容易漏 3 回滚依赖人工"三条对称排比，用户直接否决——"说没有命令行不就行了"。**只写观察到的事实，不写自己推演的后果**。这类列表既是虚构又是典型 AI 腔。
- ⚠️ **不要虚构成果的"独占性"**：用户发现的问题若对方也发现了，就不算独立动作，不值得单列成行。
- **不是"测试环境首次发版"**：准确说法是"**先在测试环境把发版跑通**"（为后续接手做准备/练手）。用"首次发版"会把一次验证性动作说成项目里程碑，性质不对。
- ⚠️ **禁止填写未被确认的时间节点**：deadline、"计划 X 日前"、耗时天数，一律不写，除非用户明确说过。
- 交付物默认同时给 Markdown + HTML（A4 打印友好，白底）。
- **用户给的时间点 ≠ 工作只在这些天做**（已踩坑两次）：用户口述的时间线（8/5 发清单、8/12 给仓库、8/19 派集群）是**组长交代任务的节点**，不是工作区间。典型：文档学习贯穿整个 8 月，不能框死在"第一周/前两周"。用户没讲到的周次不代表没做事，要留"持续进行/贯穿全月"的口子。
- **时间粒度**：月报用周/旬，只有离散客观事件（服务拆分、发现配置缺失）才精确到日；"预计完成"列绝不写精确日期。不要写"耗时 N 天"。
- **日期节点表必须有"结果/当前状态"列**：只写"发生了什么"没有结果 = 流水账，用户会质疑；补上结果列后就是任务记录，日期才站得住。判断标准：有结果 → 保留精确日期；只有动作 → 改成周/旬粒度。
- **用户会手工删改 md，改完要两版对齐**：每轮先 Read 用户的 md 最新版再动手，且改动后必须同步 HTML（md 与 html 易出现段落增删不一致，如"版本标识方式"段被删）。
- **如实分档暴露能力边界**：用"较熟悉 / 一般了解 / 待补齐"三档表替代笼统的"学习覆盖面"，比假装全会更可信，用户认可这个写法。
