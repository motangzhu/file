AI Agent 架构原理详解

从一次提问到任务完成的完整闭环

面向工程视角 · 不涉及具体厂商实现 · 概念可迁移到任意 Agent 产品

一句话结论：Agent 并不是"更聪明的模型"，而是用确定性代码包住一个概率性内核，再靠"执行—观察—再决策"的循环把它收敛到结果。架构里只有模型层是不确定的，其余五层都是工程问题。

1 · Agent 与 Chatbot 的分界

大语言模型本身是一个无状态的条件概率续写器：给它一段文本，它预测下一段最可能的文本。它不会"记得"上一秒说过什么，除非你把上一秒的内容重新放进输入里。它也不能真的打开文件、执行命令、访问网络。

Agent 在这之上加了四样东西：

增量解决什么没有它会怎样
工具让输出能作用于真实世界只能说，不能做
循环让多步任务能逐步推进只能一步到位，做不了复杂事
状态让每一步的结果能被下一步看到每步都从零开始，无法累积
停止条件让循环能收敛而不是空转无限循环或过早放弃

判定一个系统是不是 Agent，只看一条：它能不能自己决定"下一步做什么"，并为此承担多步执行的后果。能自动规划步骤、选择工具、根据结果调整策略——这才是 Agent。只会按预设流程调几次接口的，叫工作流。

Agent = 模型（决策）× 工具（能力）× 循环（收敛）× 上下文（状态） 四项是乘法关系，任何一项为零，整体就退化

能力上限由短板决定

Agent 的能力边界是 工具集 与 模型判断力 的交集。工具没提供的能力，模型再聪明也变不出来；模型判断不了的局面，工具再多也用不对。很多"Agent 做不到"的问题，根因在工具层缺失，而不是模型不够强。

2 · 运行时五层架构

无论产品形态如何，Agent 的运行时都可以拆成五层。关键不在于分层的名字，而在于认清哪一层是不确定的。

层职责确定性典型失效
宿主层会话生命周期、权限审批、文件与进程沙箱、结果呈现确定权限卡死、路径错误
编排层拼装上下文、驱动循环、调度工具、判断何时停确定循环失控、上下文超限
模型层读上下文，产出思考、文本或结构化工具调用概率幻觉、误判、提前终止
工具层提供可调用能力，返回字符串结果确定参数错误、输出过长
记忆层短期上下文与长期文件存储、检索确定写了不读、读了不信

工程含义：既然只有模型层不确定，那么提升 Agent 可靠性的主要手段，就不是"换个更强的模型"，而是用其余四层去约束它——收紧工具权限、缩短上下文、把关键状态外置到文件、给循环加硬上限。

3 · Agent Loop：唯一的引擎

Agent 的全部行为都发生在一个循环里，通常被称为 ReAct 范式（Reason + Act）。拆细一点是五个阶段。

1 · 接收 Intake

宿主层把用户消息与上下文包裹拼成一次模型请求。这一阶段出错，后面全跟着偏。

2 · 推理 Reason

模型读完整上下文，产出内部思考，然后决定：直接回答，还是发起一次工具调用。

3 · 行动 Act

宿主层解析 tool_call，真正执行。执行发生在宿主侧，模型只是"请求"，不直接动手。

4 · 观察 Observe

工具输出（包括报错）作为一条结果消息，追加进上下文。这是模型获得新信息的唯一通道。

5 · 判定 Decide

编排层判断：继续循环、正常结束、还是强制中断。回到阶段 2，直到收敛。

一次循环在协议层长什么样

模型不输出自然语言指令，而是输出结构化的调用请求：

// 模型输出（assistant message）
{
  "role": "assistant",
  "content": null,
  "tool_calls": [{
    "id": "call_01",
    "type": "function",
    "function": {
      "name": "Read",
      "arguments": "{\"file_path\":\"/etc/nginx/conf.d/app.conf\"}"
    }
  }]
}

// 宿主执行后回灌（tool message）
{
  "role": "tool",
  "tool_call_id": "call_01",
  "content": "upstream backend { server 10.0.1.11:8080; ... }"
}

关键点在于：结果是以普通消息的形式塞回上下文的。模型"看到"工具输出，和"看到"你说话，在机制上没有区别。这也解释了为什么错误信息同样有用——它也是一条新信息，能让模型自我纠正。前提是错误信息写得足够可行动。

四条停止条件

类型触发说明
自然终止模型不再请求工具，直接输出文本最常见的正常结束
预算耗尽轮数 / token / 时间到达上限兜底机制，防止无限循环
外部中断用户打断、取消、关闭会话保留已完成的部分结果
不可恢复工具连续失败、权限被拒应立刻停下并报告，而不是重试到底

收敛速度取决于信息增益

循环不是越多越好。判断一个循环是否健康，看每一轮是否显著缩小了可能性空间。如果连续两轮的观察结果没有带来新信息，就是失控前兆——要么任务本身信息不足，要么策略需要更换。这也是为什么"先查什么"比"查得多不多"更重要。

4 · 工具调用协议

工具是模型与外部世界的唯一接口。一套完整的协议包含四步：

  1. 声明：用 JSON Schema 描述工具名、参数、用途，随请求一起发给模型。描述质量直接决定调用准确率。
  2. 选择：模型根据上下文决定调用哪个工具、传什么参数。这一步是概率性的，是错误高发区。
  3. 执行：宿主层校验参数、检查权限、真正执行。模型请求不等于执行发生。
  4. 回灌：结果（或错误）作为消息追加进上下文，进入下一轮推理。

三条实践经验

错误信息要可行动

与其返回 Permission denied，不如返回"路径不存在，请先用 Glob 确认文件名"。错误信息是模型自我纠正的唯一依据。

工具描述要写"何时不用"

只写能力不写边界，模型会过度调用。明确写出"仅在 X 场景下使用，Y 场景请改用 Z"能显著降低误用。

输出必须限长

一次返回十万字符，会把上下文瞬间撑爆。超长时应截断并提示"结果已写入文件，路径为 X"。

权限边界

级别典型操作处置
只读读文件、列目录、查询、检索直接执行
可写可逆写新文件、改配置、提交代码执行但保留可回滚路径
不可逆/高危删除、生产变更、对外发送消息必须先给方案，经确认再执行

5 · 上下文工程

这是决定 Agent 表现的实际瓶颈。上下文窗口不是内存，而是注意力预算：塞得越满，模型对每条信息的关注度越低，越容易漏掉关键指令。

三种典型病理

病理表现成因
污染一个错误事实被后续轮次反复引用，越错越肯定幻觉内容进入上下文后被当作既定事实
分心忽略开头的关键约束，被无关细节带偏上下文过长，注意力被稀释
冲突在两种说法之间摇摆，无法确定上下文里存在互相矛盾的信息源

对应的处置：污染要尽早纠正并强制重新读取真实来源；分心靠压缩和卸载，并把关键约束放在上下文靠后的位置；冲突必须显式指定权威来源（例如"以控制台实际配置为准，文档仅作参考"）。

四种治理手段

四者的区别很关键：卸载和压缩是在现有上下文内部做减法，治标；检索和隔离是改变内容进入上下文的方式，治本。复杂任务优先用隔离——让子代理在独立上下文里消耗大量 token，只把结论回传主上下文，这是最有效的扩展手段。

装配优先级

上下文不是简单堆叠，而是有优先级的取舍。当空间不足时，保留顺序大致是：

  1. 当前这条用户消息（最高权重，最新指令优先）
  2. 系统约束与不可协商的安全边界
  3. 最近几轮的工具结果与观察
  4. 任务相关的记忆与结论
  5. 早期的历史对话（最先被压缩）

6 · 记忆系统

模型本身不记忆，所有"记性"都来自外部存储。分三层：

层载体生命周期容量代价
短期上下文窗口单次会话有限高，占用注意力预算
长期磁盘文件（如 MEMORY.md、日志）永久大低，但必须主动读才生效
检索索引或向量库永久很大需要检索成本

写入时机

记忆不是随时都该写。合理的触发点是：得出了可复用结论、完成了阶段性工作、发现了项目约定或用户偏好、即将超出上下文上限。把过程中的琐碎中间态写进记忆，反而会污染未来的检索。

渐进式披露

记忆文件应当分层：索引层（有哪些主题）→ 摘要层（每个主题的结论）→ 全文层（完整过程）。加载时按需逐级下钻，而不是一次性全量灌入。这和上下文工程里的检索策略是同一套思路。

三种失效模式

写了不读

结论躺在文件里，但没有任何机制在需要时去加载它。记忆文件的价值不在写入，在于被检索到。

读了不信

检索到的内容与模型先验冲突，模型选择相信自己的训练数据。需要在提示里显式指定权威来源。

记了错的

把中间态的错误结论固化进长期记忆，之后每次都被检索出来放大。记忆需要定期审计。

7 · 规划与任务分解

简单任务直接执行即可，但以下几类任务必须先规划：

  • 步骤不少于三步，且存在依赖关系
  • 包含不可逆操作
  • 需要跨多个文件、系统或服务协调
  • 中间产物需要用户确认才能继续

任务清单的三重作用

把计划写成一个显式的任务列表，看起来是多此一举，实际上解决三个问题：

  1. 给模型一个外部状态：长任务里模型容易"忘了做到哪、还剩什么"，清单把它外置成可读取的结构。
  2. 给用户进度可见性：不必等最终结果，中途就能判断方向是否跑偏。
  3. 支持断点续做：失败或中断后，可以从未完成项继续，而不是整体重来。

计划模式的意义：对于高风险任务，把"先出方案、确认后再执行"作为默认，而不是"先做再说"。不可逆操作一旦执行，再好的回滚方案都不如没发生过。

8 · 可靠性工程

Agent 会犯错，这是架构决定的，无法消除，只能约束。可靠性设计围绕一个原则展开：任何动作都应该可落地、可验证、可回滚。

变更四问

在评估任何一次变更前，按顺序回答：

顺序问题回答不了就别做
1影响范围是什么不知道波及面 → 先停下来查清
2怎么回滚回滚方案不存在 → 风险等级直接判高
3具体操作步骤步骤描述含糊 → 无法评审，也无法复现
4怎么验证成功没有验证方法 → 无法判断完成，等于没做完

风险分级

等级判定标准处置
低只读操作，无副作用直接执行
中改变状态但可逆执行，但保留回滚路径
高不可逆，或影响面超出单个服务先出方案，确认后再动

发布类任务的五个必备要素

涉及服务发版时，方案里缺任何一项都不算完整：

  1. 版本号——明确要发布的制品版本，可追溯
  2. 灰度策略——金丝雀、分批、还是蓝绿，比例与节奏
  3. 发布步骤——按序列出，每步可独立验证
  4. 观测验证——看哪些指标、在什么时间窗内、达到什么阈值算通过
  5. 回滚条件——触发即回滚的量化阈值，而不是"感觉不对就回滚"

9 · 一次任务的完整时间线

用一个运维场景把前面所有环节串起来：用户报告"网关返回 502，帮我查一下"。

轮模型判断动作观察状态
1信息不足，先看现象读取用户提供的日志片段502 集中在某时段，非全时段继续
2按链路定位，先查网关与 CLB检查负载均衡健康检查状态后端节点全部标记异常收敛
3问题在后端，查实例状态查询后端服务实例列表与事件实例出现 OOM 重启记录收敛
4需要确认根因，查监控拉取内存监控与 GC 日志内存持续增长，无有效回收确认根因
5信息足够，输出结论——结束

对照闭环的五阶段：第 1 轮是接收 + 推理，发现缺信息所以不急着下结论；第 2 到 4 轮是完整的行动—观察—判定循环，每一轮都显著缩小了排查范围；第 5 轮达到自然终止条件。

注意这个案例里没有发生的两件事：一是模型没有在第一轮就凭"502"猜测根因（避免污染）；二是每一轮的观察都带来了新信息（保证收敛）。这两点正是循环健康与否的判断标准。

反例：如果第 3 轮的观察是"实例状态正常"，而第 4 轮仍重复查询同样的实例，那就是零信息增益的死循环。此时正确做法不是继续循环，而是中断并更换策略——换个排查方向，或者直接要求补充信息。

10 · 失败模式与排查

症状可能根因处置
反复调用同一个工具，参数几乎不变循环零信息增益中断，要求更换策略或补充信息
声称已完成，但实际没做模型提前终止要求逐项列出已完成的证据与路径
引用不存在的文件、数据或命令上下文污染或幻觉要求给出来源路径，重新读取真实内容
越做越偏，忘记最初目标上下文分心重开会话，把目标与约束写进文件
处理大段输出后开始胡说上下文接近上限压缩后继续，或把任务拆成子任务
工具报错后用同样参数反复重试未利用错误信息直接告诉它错误含义与正确做法
两个说法之间反复摇摆上下文冲突显式指定权威来源，以实际配置为准
拒绝执行某个操作触及权限边界确认是否属于高危操作，明确授权或换路径

11 · 实践清单

给使用 Agent 的人

  1. 重要结论落成文件，不要只留在对话里——对话会压缩，文件不会。
  2. 提问时给足现场信息：报错原文、配置片段、影响范围、时间窗口。
  3. 长任务要求中途写进度文件，而不是指望上下文一直完整。
  4. 不可逆操作先要方案，确认后再让对方动手。
  5. 发现方向跑偏立刻中断，不要等它自己回头。
  6. 要求给出证据路径，而不是"我记得是这样"。
  7. 上下文快满时主动要求压缩，或拆分任务。
  8. 复杂任务拆成子任务，各自用独立上下文跑。
  9. 定期清理记忆文件里的过时结论，避免错误被反复放大。
  10. 显式指定权威来源：控制台实测 > 官方文档 > 推测。

给搭建 Agent 的人

  1. 工具描述要写清"什么时候不该用"，只写能力不写边界会被过度调用。
  2. 错误信息必须可行动，这是模型自我纠正的唯一依据。
  3. 工具输出设长度上限，超长引导写入文件并回传路径。
  4. 循环必须有硬上限：轮数、token、时间，三重兜底。
  5. 只读工具与写入工具分权限，高危操作单独审批。
  6. 关键约束放在上下文靠后位置，而不是淹没在开头。
  7. 提供明确的停止信号，让模型知道何时算"做完了"。
  8. 记忆文件建索引层，支持按需下钻而不是全量加载。
  9. 子代理只回传结论，中间过程留在自己的上下文里。
  10. 记录每轮的输入输出，出问题时能完整复盘。
全文围绕一条主线：Agent 的可靠性不来自模型更聪明，而来自确定性的工程结构对概率性内核的有效约束。
