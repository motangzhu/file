Kong 与腾讯云 TKE Ingress 选型手册

面向 TKE 生产集群的接入层选型：把 TKE 的四条 Ingress 路线、Kong 的能力边界、以及腾讯云托管 Kong 与开源 KIC 的差异一次讲清。

整理时间 2026-09-03 · 结论基于腾讯云官方文档与 Kong 官方 支持策略页，文中标注了需要你二次核验的点。

先看四条结论

1. TKE 上的 Ingress 不是一种技术，是四条路线。应用型 CLB（默认，ingress.class: qcloud）、Nginx Ingress（扩展组件 已停止维护）、云产品托管（API 网关 / 云原生网关 Kong）、Others（自建 Kong/APISIX/Traefik，自定 IngressClass）。选型的本质是在「运维成本」和「路由/治理能力」之间取点。

2. 2026 年最大的变量是 Nginx Ingress 退役，这事已经过了讨论期。上游社区 ingress-nginx 于 2025-11 宣布退役，best-effort 维护持续到 2026-03，之后归档，不再有 release、bugfix 和安全补丁。TKE 的 NginxIngress 扩展组件也已停止版本更新和维护，官方明确「兼容性不受影响，但需自建或走应用市场」。继续用 = 自己承担 CVE 风险。

3. Kong 在腾讯云上有两种落法，差别是「控制面归谁运维」，不是功能多少。形态 A 用腾讯云云原生网关（TSE/TSF 托管，内核为开源 Kong，兼容 Kong 3.x），网关实例在集群外；形态 B 是在 TKE 集群内用 Helm 自建 Kong Ingress Controller（KIC），数据面是集群里的 Pod。

4. 两个必须核验的硬约束。其一，云原生网关（含 Kong 形态）目前仅对微服务场景开放白名单新购，即作为 Polaris（北极星）服务接入层的场景，其余场景不支持新接入，非支持场景控制台会重定向到北极星控制台。其二，托管版 Kong Ingress Controller 官方文档列出的支持版本仍是 2.7.0 / 2.5.0 / 1.3.4，与开源主线 3.5.x 差距明显 —— 这直接决定你能不能用上新版插件和 Gateway API 能力。高风险

1. TKE Ingress 四条路线

路线控制器 / 数据面特点适用场景与代价
应用型 CLB
qcloud		 TKE Ingress Controller + 腾讯云 CLB（集群外托管） 不写 ingress.class 或写 qcloud 即由它接管。一条 Ingress 绑定一个 CLB 实例（一个 IP）。CLB 经 NodePort 转发到 Pod；集群支持 VPC-CNI 时可直连 Pod。 简单七层路由、对 IP 收敛不敏感的场景。代价：路由一多，CLB 实例数量和公网 IP 数量线性增长，成本和管理成本都上去了。
Nginx Ingress CLB + 集群内容器化 nginx CLB 之后多一层 nginx 代理，通过 Annotation 扩展原生 Ingress。IP 收敛：多个 Ingress 共用一个 CLB。 需要较复杂路由规则且要收敛 IP。三种部署方案中官方推荐 Deployment + LB 直连 Pod（性能好、免人工维护 CLB），前提是集群使用 VPC-CNI 或 Global Router 且已开启 VPC-CNI 混合。
云产品托管 专享型 API 网关 / 云原生网关（Kong） 网关在集群外，直连 TKE 的 Pod，无中间节点。自带认证鉴权、流控、灰度分流、缓存、熔断降级。 多集群统一接入层、需要 API 治理能力。代价是引入云产品依赖与额外费用，且受上文的白名单与版本限制。
Others（自建） 自己装的 Kong / APISIX / Traefik / Envoy Gateway 等 TKE 不托管，需自行安装对应 Ingress Controller，并在 Ingress 上指定 IngressClass。TKE 官方对此路线不提供 SLA。 需要 Kong 完整插件生态、或想上 Gateway API、或已有自建网关标准。代价：版本升级、CVE 修复、容量规划全部自理。

多控制器共存：TKE 允许集群内同时存在多个 Ingress Controller，靠 kubernetes.io/ingress.class 或 spec.ingressClassName 区分归属。这让「老的 CLB Ingress 不动、新业务走自建 Kong」这种渐进迁移成为可能，是迁移期最实用的抓手。

2. CLB Ingress 要点

默认路线，也是很多团队的起点。几个在生产上踩过坑的点：

  • IP 不收敛：一条 Ingress = 一个 CLB 实例 = 一个 IP。域名多、路由多时，CLB 实例费 + 公网 IP 费会明显超过自建网关的节点成本。
  • 直连 Pod 需要 VPC-CNI：不开直连时走 NodePort，多一跳转发，且必然 SNAT，流量集中时容易出现端口耗尽或 conntrack 插入冲突导致丢包；同时 CLB 绑大量节点的 NodePort 会造成全局负载不均、健康检查探测包放大。
  • 关键 annotation（TKE 扩展，创建后不可改的居多）： 
    kubernetes.io/ingress.class: qcloud                    # 指定控制器，缺省即 qcloud
kubernetes.io/ingress.existLbId: lb-xxxxxxxx           # 复用已有 CLB
kubernetes.io/ingress.subnetId: subnet-xxx             # 创建内网 CLB
kubernetes.io/ingress.internetChargeType: TRAFFIC_POSTPAID_BY_HOUR
kubernetes.io/ingress.internetMaxBandwidthOut: "10"    # 1-2048 Mbps，仅公网
kubernetes.io/ingress.qcloud-loadbalance-id            # 只读，控制器回写
  • 计费类型与带宽只在创建时生效，创建后修改 annotation 无效 —— 这是常见的「改了没效果」来源。

3. Nginx Ingress 现状与三种部署方案

三种方案对比

方案优点缺点 / 适用
Deployment + LB最简单，CLB 绑各节点 NodePort，节点增删自动同步多一跳 + SNAT，大并发下有端口耗尽与 conntrack 冲突风险。性能要求不高时可用。
DaemonSet + HostNetwork + LBCLB 直绑节点 IP:80/443，性能好需人工维护 CLB 与边缘节点，无法自动扩缩容。官方不推荐。
Deployment + LB 直连 Pod性能好，无需人工维护 CLB推荐方案。要求集群用 VPC-CNI，或 Global Router 且已开启 VPC-CNI（混合模式）。

维护状态（必读）：容器服务扩展组件 NginxIngress 已停止版本更新和维护，官方说明为「核心代码完全遵循开源版本，兼容性不受影响，您仍可通过自建方式或 TKE 应用市场继续使用」。结合上游 ingress-nginx 2026-03 归档，这意味着：继续用 Nginx Ingress = 自行承担安全补丁责任。阿里云 ACK 已公告同类组件 2026-11-30 后停止维护并建议迁移到 APIG/ALB Ingress 或 Gateway API，行业方向一致。中高风险

4. Kong 是什么

Kong 的定位是 API 网关，不是单纯的 Ingress Controller。它的数据面基于 OpenResty（Nginx + Lua），控制面提供 Admin API 与声明式配置。理解这一点很重要：它能在 Ingress 之外额外提供鉴权、限流、熔断、请求转换、可观测等能力，代价是概念更多、运维更重。

三层身份，别混

  • Kong Gateway：数据面本体，处理请求。开源版 + 企业版。
  • Kong Ingress Controller（KIC）：Kubernetes 控制器，watch 集群里的 Ingress / Gateway API / Kong CRD，翻译成 Kong Gateway 的配置。不处理流量。
  • Kong Operator：Kong 主推的 Kubernetes 原生运行方式，接管 Gateway 的 day-2 运维（零停机配置更新、零停机升级、证书轮换、自动扩缩）。这是新方向的落点。

5. Kong 对象模型

Kong 比 Kubernetes Ingress 多一层抽象，这是插件能挂上去的原因：

对象职责KIC 中的来源（K8s 映射）
Route入站匹配规则：host、path、header、method、SNIIngress（每条 path 一条）或 Gateway API 的 HTTPRoute / GRPCRoute / TCPRoute
Service上游服务的抽象：协议、host、端口、超时、重试Kubernetes Service 自动生成同名 Kong Service
Upstream负载均衡池 + 健康检查 + 算法（一致性哈希等）Kubernetes Service 自动对应；细粒度策略用 KongUpstreamPolicy
Target具体后端实例 IP:Port（含权重）Endpoints / EndpointSlice 自动同步
ConsumerAPI 调用方身份，是 key-auth / JWT / ACL 等插件的挂载主体KongConsumer CRD
Plugin横切能力，可作用于全局 / Service / Route / ConsumerKongPlugin CRD + konghq.com/plugins 注解

实用心智模型：K8s 的 Service 在 Kong 里被拆成两半 —— 不变的「Service」和可调优的「Upstream/Target」。所以灰度权重、健康检查阈值这类东西，在 nginx ingress 里要写 annotation，在 Kong 里是 Upstream 的一等字段。

6. 部署模式与插件

DB-less vs DB-backed

模式说明取舍
DB-less（声明式）无数据库，配置以声明式文件（或 K8s CRD）形式加载进内存Kubernetes 场景首选。配置即 Git 里的 YAML，可版本化、可回滚、可 Code Review。KIC 3.x 的 Helm chart 默认 router_flavor: expressions。
DB-backed配置存 PostgreSQL，多节点共享适合 Kong 集群规模大、需要 Admin API 动态改配置的场景。代价是多一个数据库要运维，且配置漂移风险高。Helm 默认用 traditional_compatible 路由引擎以兼容存量配置。

插件

  • 开源插件覆盖：认证（key-auth / JWT / OAuth2 / basic-auth）、安全（CORS / IP 黑白名单 / bot-detection）、流控（rate-limiting / request-termination）、可观测（prometheus / zipkin / opentelemetry / file-log / http-log）、转换（request-transformer / response-transformer / cors）。
  • 企业版独有：OIDC、高级 RBAC、Workspaces、Dev Portal、Vitals 等。
  • 注意：插件配置里引用 Secret 时，KIC 3.4.15 及之前存在 GO-2026-5010（Secret-backed plugin 配置经非敏感 diagnostics 端点泄漏）的 Moderate 级漏洞，需升级到修复版本。

8. Ingress → Gateway API

Ingress API 已 feature-frozen，Gateway API 是官方指定的方向。Kong 是 Gateway API 最早、最完整的实现者之一，同时仍继续支持 Ingress 资源（只要 Kubernetes API 还允许）。

Gateway API 的三层角色模型

  • GatewayClass —— 基础设施提供方定义控制器类型
  • Gateway —— 集群运维定义入口（listener、端口、TLS 证书）
  • HTTPRoute / GRPCRoute / TCPRoute —— 应用开发方定义路由逻辑（权重、header 匹配、filter）

相比 Ingress 的核心改进：角色分离 + 标准化字段取代 annotation sprawl + 原生权重分流 + 完善的 status 字段（排障时能直接看出资源是否被 accept、programmed）。

KIC 3.5 的废弃项映射

已废弃（仍可用，有告警）迁移目标说明
KongIngressKongUpstreamPolicy路由与服务级配置已改用专用 annotation，如 konghq.com/https-redirect-status-code
TCPIngressTCPRoute（Gateway API）未来版本将移除
UDPIngressUDPRoute（Gateway API）未来版本将移除

迁移工具

  • ingress2gateway：SIG Network 官方工具，2026-03 发布 1.0。支持 30+ 个 ingress-nginx annotation（CORS、后端 TLS、正则匹配、路径重写等），并有控制器级集成测试验证行为等价性。会明确告警无法翻译的配置。
  • Kong 也维护了自己的 ingress2gateway 路径与文档（--providers=ingress-nginx）。
# 安装
go install github.com/kubernetes-sigs/ingress2gateway@v1.0.0
# 或 brew install ingress2gateway

# 按命名空间导出（推荐先小范围试）
ingress2gateway print --namespace my-api --providers=ingress-nginx > gwapi.yaml

# 全集群导出
ingress2gateway print --providers=ingress-nginx --all-namespaces > gwapi.yaml

工具是迁移助手，不是一键替换。导出的 YAML 必须逐条人工复核，尤其是 configuration-snippet 这类任意 nginx 指令 —— 它们不可翻译，也没有等价物。

9. 腾讯云云原生网关 Kong × TKE

产品定位

腾讯云云原生网关（微服务引擎 TSE / 微服务平台 TSF 下的组件）内核基于开源 Kong，兼容 Kong 3.x 等主流版本，定位为「流量网关 + 安全网关 + 微服务网关」三合一托管产品。官方宣称 100% 兼容开源、支持自定义插件、控制台可批量改系统参数（请求体大小、TLS 版本等）、支持多可用区与网关数据备份。

对接 TKE 的两种方式

方式一：服务来源关联（控制台手动）

控制台路径：云原生网关实例 → 服务路由 → 服务来源 → 新建，来源类型选「容器服务」，实例选与网关同 VPC 的 TKE 集群。然后在服务路由 → 服务 → 新建，服务类型选「K8S 服务」，填写命名空间和服务名，最后配路由规则（请求方法 / 路径 / Host 至少配一种）。

适用：服务数量少、变更不频繁、不希望网关 watch 集群全部资源。

方式二：开启托管 Kong Ingress Controller

控制台路径：TSF 控制台 → 云原生网关 → 实例详情 → Ingress → 关联容器集群。可关联同 VPC 或通过 云联网 CCN / 对等连接 打通的集群。开启后网关直接监听容器集群变化并同步配置，Ingress 资源里把 ingress.class 设成对应 IngressClass（默认 kong，可自定义）即可。

apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: demo-v1
  annotations:
    konghq.com/plugins: "httpbin-auth"
spec:
  ingressClassName: kong
  rules:
  - http:
      paths:
      - path: /demo-v1
        pathType: Prefix
        backend:
          service:
            name: nginx
            port:
              number: 80

三个必须向腾讯云确认的点高风险

  1. 新购限制：官方文档明确「目前云原生网关仅对微服务场景，即作为 Polaris（北极星）服务接入层支持开通白名单新购，其余场景不支持新接入」。如果你的场景不是北极星接入层，需要先提工单确认能否开通。
  2. KIC 版本落后：文档列出的支持版本为 2.7.0 / 2.5.0 / 1.3.4，而开源 KIC 已到 3.5.x。2.x 与 3.x 在路由引擎、CRD、Helm-only 安装、废弃项上差异巨大。请直接找腾讯云确认托管版内核与 KIC 的实际版本、以及 Gateway API 支持到哪一版。
  3. 多集群限制：文档注明「仅 Ingress 2.7.0 支持关联多个容器集群」。如果你打算用一套网关管多个 TKE 集群，这是硬门槛。

形态 A vs 形态 B 的取舍

维度形态 A · 托管云原生网关形态 B · 集群内自建 KIC
运维主体腾讯云托管，免底层运维自己管版本、CVE、容量
版本可控性跟随云产品节奏，落后开源主线完全自主，可立即上 3.5.x
网络要求网关与集群同 VPC / CCN / 对等连接；直连 Pod，无中间节点在集群内，网络路径最短
多集群统一接入天然支持（受版本限制）需自行部署多套 + 外部 LB 聚合
CI/CD 集成部分配置在控制台，GitOps 需额外打通Ingress/CRD 即 YAML，天然 GitOps
成本网关实例费节点资源 + 人力

10. 选型决策

决策顺序建议（按你自己的排查习惯：先看影响范围，再定方案）：

  1. 只是简单七层路由、域名不多 → 继续用 CLB Ingress（qcloud）。它受腾讯云 SLA 保障，运维成本最低。注意 IP 不收敛的成本拐点。
  2. 需要 IP 收敛 + 较复杂路由，且能接受自担安全风险 → 短期可继续用 Nginx Ingress（走 Deployment + LB 直连 Pod 方案，需 VPC-CNI），但必须排迁移计划。
  3. 需要 API 治理（鉴权/限流/灰度/插件），且已是北极星微服务体系 → 走形态 A 托管云原生网关，先提工单确认开通与版本。
  4. 需要 Kong 完整能力 + 版本自主 + GitOps → 走形态 B，集群内自建 KIC 3.4 LTS（或 3.5.x），前端挂 CLB。
  5. 新建集群 / 新业务 → 直接上 Gateway API + Kong，别再从 Ingress 起步。

11. 发布与回滚方案

以下以形态 B（集群内自建 KIC）替换现有 Nginx Ingress 为例，风险等级 中。版本号、灰度、步骤、观测、回滚五项齐全。

版本号

  • Helm chart：kong/kong，KIC 3.4.x（LTS，EOL 2027-12-18）；若集群已用 Gateway API 1.3 则选 3.5.x。
  • Kong Gateway 镜像：kong:3.9.x 或更高（3.4.x–3.12.x 与 KIC 3.x 全系兼容），不要用 EOL 版本。
  • Gateway API CRD：与 KIC 版本对应（3.4 → 1.2，3.5 → 1.3），用 Standard Channel。
  • 前置于 Kong 的 CLB：复用现有 VIP 或新建，创建时一次性确定计费类型与带宽。

灰度策略

  • 按域名灰度（推荐，最可控）：先在 Kong 上发布非核心域名，验证通过后再逐个迁移核心域名。同一时刻两套 ingress 并存，靠 DNS/CLB 转发规则切流。
  • 按流量比例灰度：核心域名用 Gateway API 的 backendRefs 权重，从 5% → 20% → 50% → 100% 递进。CLB Ingress 路线不支持权重，只能靠调整后端 RS 权重实现，粒度更粗。
  • 发布窗口：选业务低峰，每次只切一个域名，切完观察 30 分钟再进入下一个。

发布步骤

  1. 前置检查：确认集群网络模式（是否支持 VPC-CNI 直连 Pod，决定 CLB 到 Kong 的链路）；确认 Gateway API CRD 已安装且版本匹配。
  2. 安装 CRD（Helm 不管 CRD）： 
    kubectl kustomize https://github.com/Kong/kubernetes-ingress-controller/config/crd?ref=v3.4 \
  | kubectl apply -f -
  3. Helm 安装 KIC 到独立 namespace（如 kong），ingressController.ingressClass 设为 kong，不要覆盖已有的 nginx / qcloud。
  4. 先建灰度 Ingress/HTTPRoute，指向与现网相同的后端 Service，用非核心域名验证。
  5. 逐域名切换，每切一个观察 30 分钟。
  6. 摘除旧控制器：确认全部流量已迁走，再下线 nginx ingress。

观测验证

  • Kong 侧：开启 prometheus 插件，重点看 kong_http_requests_total（按 route/service 与 status 分组）、kong_upstream_target_health、延迟分位。
  • 控制器侧：kubectl -n kong logs deploy/<kic> 看配置同步是否有 translation error / config push failed。
  • CLB 侧：腾讯云可观测平台看 CLB 的后端健康检查异常数、出带宽、连接数、5xx 状态码。
  • 业务侧：对比切换前后的错误率、P99 延迟、QPS。Kong 与 nginx 的默认超时、body size 限制不同（如 nginx 的 proxy-body-size、proxy-read-timeout），最容易在这里出差异。
  • 日志：Kong 的 http-log / file-log 插件接入 CLS，用于比对请求路径是否与预期一致。

回滚条件与操作

触发条件回滚动作影响范围
切换后 5 分钟内 5xx 比例 > 1%，或 P99 延迟上升 > 50%将该域名的 Ingress/HTTPRoute 改回原 IngressClass；或 DNS 回切单域名，秒级
Kong Pod 反复 CrashLoop / 配置同步持续失败helm rollback -n kong <release>全部走 Kong 的域名
某插件导致请求被错误拦截（如限流阈值过小）删除对应 KongPlugin 或摘掉 konghq.com/plugins 注解该插件作用的 route/service
CLB 健康检查批量失败检查 Kong Pod 就绪探针与 CLB 安全组；必要时 CLB 后端切回原 nginx全量

回滚前置条件：旧控制器在整个灰度期必须保持原样不下线，且 CLB/DNS 的回切路径提前演练过一次。没有演练过的回滚方案不算回滚方案。

  - name: https

      certificateRefs:
      - name: prod-tls

apiVersion: gateway.networking.k8s.io/v1
kind: HTTPRoute
metadata:
  name: demo
spec:
  parentRefs:
  - name: prod-gw
    namespace: kong
  hostnames: ["demo.example.com"]
  rules:
  - matches:
    - path: { type: PathPrefix, value: / }
    backendRefs:
    - name: nginx
      port: 80
      weight: 90      # 灰度：9:1
    - name: nginx-canary
      port: 80
      weight: 10

13. 排查清单

沿用你的链路排查习惯，从外到内逐段验证：客户端 → DNS → CLB → Kong（数据面）→ KIC（控制面同步）→ K8s Service → EndpointSlice → Pod。

  1. 请求根本没到 CLB：检查 DNS 解析、CLB 安全组放通 80/443、CLB 是否被 ACL/安全组拦截。跨地域走 CEN 的，确认云联网带宽与路由。
  2. CLB 健康检查失败：Kong Pod 是否 Ready；CLB 到 Pod 的探测端口是否正确；VPC-CNI 直连模式下注意节点安全组。
  3. 到 Kong 但返回 404（no Route matched）：Ingress 的 ingressClassName 是否等于 KIC 配置的 ingressClass；Host 是否匹配；pathType 是否写对（Prefix vs ImplementationSpecific）。
  4. 返回 401/403：插件作用范围（全局 / Service / Route / Consumer）是否符合预期；KongConsumer 凭证是否创建。
  5. 返回 503（no healthy upstream）：EndpointSlice 是否有可用 Target；Upstream 健康检查阈值是否过严；服务刚发布时 Target 还没同步。
  6. 配置改了不生效：看 KIC 日志是否有 translation error；CRD 是否在升级后忘了单独 apply；是否存在多个控制器抢同一个 Ingress。
  7. 性能问题：Kong 的资源 requests 是否给够；HPA 是否触发；CLB 走 NodePort 时检查节点 conntrack 表与端口占用。
  8. 跨网段不通：云原生网关与 TKE 集群需同 VPC，或用 CCN / 对等连接打通；安全组、CFW、网络 ACL 逐层确认。
