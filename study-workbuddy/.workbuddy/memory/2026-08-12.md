# 2026-08-12 学习记录

## KubeSphere 搭建（续，KubeKey v4.0.5 重大发现）

### 关键：KubeKey v4.0.5 是「双文件」模型（和 v3 的 kind: Cluster 单文件完全不同）
- `kk create config --with-kubernetes v1.34.3` 生成的是 **`kind: Config`**（`apiVersion: kubekey.kubesphere.io/v1`），只含组件（kubernetes/etcd/cri/cni/storage_class/dns），**不含节点**。
- 节点清单需另用 **`kk create inventory -o inventory.yaml`** 生成（`kind: Inventory`）：`spec.hosts.<name>.connector{type:ssh,host,port,user,password|private_key}` + `internal_ipv4`；角色在 `spec.groups`（k8s_cluster→kube_control_plane/kube_worker，etcd）。
- 建 K8s 命令：**`kk create cluster -i inventory.yaml -c config.yaml`**（注意是 `-i`/`-c`，不是 v3 的 `-f`）。
- ⚠️ **`--with-kubesphere` 在 v4.0.5 已被完全移除**（实测 `kk create config` 和 `kk create cluster` 都报 `unknown flag`）。所以 **kk v4.0.5 不再负责装 KubeSphere**——K8s 用 kk 建，KubeSphere v4 用官方 Helm chart（ks-core）单独装到已存在集群（两阶段）。详见下方"重大更正"。
- 旧 v3 写法（hosts/roleGroups/addons、kind: Cluster、-f config-sample.yaml）在 v4.0.5 **已全部失效**，文档第4、5节已整体重写为双文件模型。

### v4 存储配置（config.yaml 的 spec.storage_class）
- 默认 `local.enabled:true, default:true`（OpenEBS localpv，零依赖，满足 KubeSphere 装前置"需默认 SC"）。
- 启用 NFS：`nfs.enabled:true` + `nfs_provisioner_version:"4.0.18"` + `nfs.server:192.168.85.104` + `nfs.path:/data/nfs`。NFS 作为额外 SC（名 nfs-client）。
- 若要把 NFS 设默认：local.default:false + nfs.default:true（v4.0.5 支持，但需实测；不稳就回退 local 默认）。
- 旧版 `addons` + `nfs-subdir-external-provisioner` 写法在 v4 已不适用。

### 实战踩坑：inventory.yaml 的 etcd 组（两次纠错后的最终结论）
- 用户 08-12 跑 `kk create cluster -i inventory.yaml -c config.yaml`（已去掉 --with-kubesphere）后，master01 的 `Run kubeadm init` 失败：`[ERROR ExternalEtcdVersion]: Get "https://192.168.85.101:2379/version": connection refused`。
- **我第一版推断错**：以为"删掉 etcd 组 → 堆叠 etcd 自动部署"。用户照做后 precheck 直接报 `etcd group must not be empty` —— 证明 **etcd 组必须非空**（KubeKey v4 强制）。
- **最终正确机制（已查证官方 pkg.go.dev 文档 + gitee kubekey 研究）**：
  - KubeKey v4 的 inventory 里 **etcd 组必须存在且指向 control-plane 节点**（官方默认 `kk create inventory` 就是 `etcd: hosts: [localhost]`）。
  - v4 在 etcd 组节点上以 **systemd service** 形式自动部署 etcd（不是 kubeadm 静态 Pod），再让 `kubeadm init` 以外部 etcd 方式连接它（所以才有 ExternalEtcdVersion 检查）。
  - 第一次 `ExternalEtcdVersion` 连 2379 失败 = **master01 上的 etcd systemd service 没起来**（2379 没监听），不是 etcd 组格式错。原因通常是首次装 etcd 数据/镜像问题，或上一次失败残留。
- **正确修复（不是删 etcd 组，而是保留 etcd 组 + 清理重跑）**：
  1. inventory 保留 `etcd: hosts: [master01]`（绝不能删）
  2. 清理 master01 残留：`kubeadm reset -f`（若 kubeadm 不在 /usr/bin，找 `ls /usr/local/bin/kubeadm`）+ `rm -rf /var/lib/etcd /etc/kubernetes /etc/cni/net.d`
  3. 重跑 `kk create cluster -i inventory.yaml -c config.yaml`，观察 etcd 安装步骤日志
- 其余两条 WARNING（kernel 5.14 unsupported、clusterDNS 169.254.25.10）均无害，可忽略。
- **⚠️ 第二次实战补刀（etcd 清理不彻底）**：用户清掉 kubelet 残留后重跑，kubelet precheck 过了，但又回到 `ExternalEtcdVersion 2379 refused`。根因：我上一次的清理脚本**只删了 /var/lib/etcd、/etc/etcd 数据目录，没删 etcd 二进制（/usr/local/bin/etcd）和 systemd 单元（/etc/systemd/system/etcd.service）**。KK 的 `Get installed etcd version` 在 master01 仍返回 success → 判定"etcd 已安装" → **skip 了 install/start 步骤** → etcd 从未启动 → 2379 不通。
  - **正确 etcd 清理（仅在 master01）**：`systemctl stop/disable etcd` → `rm -f /usr/local/bin/etcd /usr/local/bin/etcdctl /usr/local/bin/etcdutl` → `rm -f /etc/systemd/system/etcd.service /etc/etcd.env && rm -rf /etc/etcd /var/lib/etcd` → `systemctl daemon-reload` → 确认 `command -v etcd` 无输出。这样 KK 才会重新安装并启动 etcd。
  - **通用经验**：KK v4 的"组件已安装"判定靠二进制是否存在。任何组件（etcd/kubelet/kubeadm）残留了二进制或 systemd 单元，重跑时对应步骤就会被 skip 而留下隐患。**清理必须连二进制+systemd 单元一起删，不能只删数据目录。**
- 教训：KubeKey v4 的行为（双文件模型、flag 移除、etcd 组机制、etcd 是 systemd service）与我之前基于 v3 的记忆出入很大，**凡涉及 v4 具体操作命令，必须查官方/实测，不能凭 v3 经验推断**。

### 实战踩坑 #2：kubelet precheck 失败（也是"半安装残留"）
- 用户清掉 etcd 组又加回、重跑 `kk create cluster` 后，新报错：`[Kubernetes | Ensure kubelet service is active] run failed: The kubelet service must be running and active when it is loaded.`（3 节点全 failed）。
- **根因**：第一次 `kk create cluster`（etcd 检查挂掉那次）其实已成功装好 containerd + kubelet，kubelet 的 systemd 单元已生成（loaded），但 `kubeadm init` 在 etcd 检查就失败 → kubelet 从未启动 → 状态 loaded 但 inactive。
- **更深的坑**：之前我让跑的 `kubeadm reset -f` 当时报 `/usr/bin/kubeadm: 没有那个文件或目录`——那条清理**根本没执行**（kubeadm 真实路径在 `/usr/local/bin/kubeadm` 或 `/opt/kubekey/bin/kubeadm`，不在 /usr/bin），所以残留一直都在，每次重跑都被 precheck 拦。
- **正确修复（所有节点都跑）**：
  1. `systemctl stop kubelet; systemctl disable kubelet`
  2. 找真实路径 `KUBEADM=$(command -v kubeadm || ls /usr/local/bin/kubeadm || ls /opt/kubekey/bin/kubeadm)` 后 `$KUBEADM reset -f`
  3. `rm -rf /etc/kubernetes /var/lib/kubelet /var/lib/etcd /etc/etcd /etc/cni/net.d /var/lib/cni /var/run/kubernetes`
  4. `rm -f /etc/systemd/system/kubelet.service /etc/systemd/system/kubelet.service.d/10-kubeadm.conf; systemctl daemon-reload`
  5. 确认 kubelet 单元不再 loaded，然后重跑 `kk create cluster -i inventory.yaml -c config.yaml`
- **通用经验**：KubeKey v4 任何一次中途失败，重跑前都必须把**每个节点**的残留清干净（kubelet/etcd/kubeadm/kubernetes 目录 + systemd 单元），否则 precheck 会因上一次残留失败。且 kubeadm/kubelet/kubectl 路径在 `/usr/local/bin` 或 `/opt/kubekey/bin`，**别用 /usr/bin**。

### 实战踩坑 #3：kubelet 起不来（exit status 5，紧接 etcd 修好后）
- 用户清掉 etcd 残留重跑后，etcd 起来了（`Start and enable etcd systemd service` → success，2379 通了），但 `Run kubeadm init` 在 `wait-control-plane` 阶段 4 分钟超时：`[kubelet-start] WARNING: unable to start the kubelet service: [exit status 5]` + `The kubelet is not healthy ... 10248 connection refused`。
- **根因**：上一轮"kubelet precheck 失败"的清理脚本**只删了 kubelet 的 systemd 单元（`/etc/systemd/system/kubelet.service`）、没删 kubelet 二进制（`/usr/local/bin/kubelet`）**。KK v4 的 `Check if kubelet is installed` 只看二进制是否存在 → 判定 kubelet 已装 → 整段 `Copy kubelet systemd service file / Reload and enable kubelet service` 被 skip（日志 3 节点全是 skip）→ 单元一直缺失 → `systemctl start kubelet` 报 **exit status 5**（systemd 的 LSB "program is not installed" = unit 文件不存在）→ kubelet 起不来。
- **`exit status 5` 含义关键**：它不是"启动失败"，而是"unit 不存在"。别去调 kubelet 配置/参数，直接恢复 unit 才是正解。
- **正确修复**：
  1. 三节点：`rm -f /usr/local/bin/kubelet`（删二进制，KK 才会重装单元）+ `rm -f /etc/systemd/system/kubelet.service /usr/lib/systemd/system/kubelet.service; rm -rf /etc/systemd/system/kubelet.service.d; systemctl daemon-reload`
  2. master01 额外：`kubeadm reset -f`（路径 /usr/local/bin/kubeadm）+ `rm -rf /etc/kubernetes /var/lib/kubelet /etc/cni/net.d /var/lib/cni /var/run/kubernetes`
  3. 重跑 `kk create cluster -i inventory.yaml -c config.yaml`，确认 `Copy kubelet systemd service file` 从 skip 变 success
- **铁律（已写进手册附录 B 顶部）**：KK v4 判定"组件已安装"只看二进制。清理残留必须**二进制+systemd 单元一起删**，只删单元不删二进制 = KK skip 重装单元 = 留下 exit status 5（kubelet）/ 2379（etcd）这类坑。etcd 与 kubelet 是同一类坑，修复手法一致（删对应二进制 + 单元 + daemon-reload）。

### 手册修正：kubectl `/usr/bin` 软链其实是多余的（用户 10:11 追问后纠正）
- 之前第 6 节给的修法是"把坏链指回真身"（`ln -sf /usr/local/bin/kubectl /usr/bin/kubectl`）。用户问"那软链接是不是多余的"——**确实多余**：`/usr/local/bin` 本就在默认 PATH 里，真二进制就在那，PATH 能直接找到。`/usr/bin/kubectl` 这个链接是旧残留，且因指向不存在路径成为坏链、又因 `/usr/bin` 在 PATH 中先于 `/usr/local/bin` 命中而挡路。
- **更优修法（已改进手册第 6 节）**：直接 `rm -f /usr/bin/kubectl`（只删链接，不动真二进制，安全），让 PATH 自然用 `/usr/local/bin/kubectl`。这是最干净解。同理 `kubeadm`/`kubelet` 若也报坏链，同样 `ls -l /usr/bin/kubeadm` 看后 `rm -f` 即可。KK 自身跑任务走绝对路径不受影响。
- 结论：遇到 `kubectl/kubeadm: 没有那个文件或目录` 这类报错，先 `ls -l /usr/bin/<cmd>` 看是不是坏软链，是就直接删，不必重建链接。
