## Konga = TSE 托管 Kong 自带管理台（10:40，用户提问"Konga 使用"）
- 澄清：用户语境（TSE 托管版 Kong）里 Konga 不是第三方要装的东西，是腾讯云给托管实例自带的 Web 管理 UI——TSE 控制台实例详情页就有「Konga 控制台」页签。开源 Konga（pantsel）是自建 Kong 才需要自己部署的东西。**两套别混**。
- 登录路径：TSE 控制台 → 云原生网关实例详情 → 「访问控制」页签 → Konga 访问地址（公网/内网 :1337，可开关公网+白名单）+ admin 初始密码（仅此处展示一次，登录后必改）。
- 架构本质：Konga 只走实例内 Admin API（127.0.0.1:2001，仅内网）改配置，不经业务流量；数据面是 80/443。1337 是管理台端口，不是网关调用地址。
- 菜单映射：SERVICES=后端服务 / ROUTES=路径匹配 / UPSTREAMS=多副本负载均衡+健康检查 / CONSUMERS=调用方账号 / PLUGINS=限流缓存鉴权 / SNAPSHOTS=配置基线备份回滚 / CONNECTIONS=连多套 Kong（托管版默认已连好）。
- 最短发布流程：登录改密 → Services 新建（URL 填后端地址或 Upstream 名）→ 进 Service 建 Route（Path 是匹配规则非后端路径）→ 用网关代理地址(80/443) curl 验证。
- ⚠️ 红线：托管版 Admin API 默认不对外。官方文档教过用 Konga 建路由把 /admin-api 暴露出来（URL 填 http://127.0.0.1:2001/）——高危操作，必须挂 basic-auth，默认不做。
- 待用户确认：他问的是 TSE 托管实例的 Konga 页签，还是中间件集群自建 helm Kong 想搭 Konga UI（后者才需要部署方案）。

- 用户提到 Konga 某 Service 的 Plugins 里有 `tenant-resolver`——查证三轮：**非 Kong 官方插件（Plugin Hub 无此名），也非 TSE 预置系统插件（系统插件全为 tse-* 前缀：tse-route/tse-rate-limiting/tse-custom-auth 等 14 个）** → 判定为公司/平台自研上传的自定义插件。语义 = 从请求（子域/Header/JWT claim）解析租户并注入统一请求头（如 x-tenant-id）供后端做多租户隔离。Konga 里 ADD PLUGIN 列表读的就是实例已加载插件集合。
