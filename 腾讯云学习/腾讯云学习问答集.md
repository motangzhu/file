## Q1（2026-08-06）：腾讯云 CNB 云原生构建是什么？它和传统的 CI/CD 工具（如 Jenkins）核心区别是什么？

### 一句话理解

CNB（Cloud Native Build，云原生构建）是腾讯云的一站式开发者平台，基于 Docker 生态，用**声明式语法**把环境、缓存、插件全部抽象，覆盖「需求 → 代码 → 构建 → 制品 → 部署」全流程。它不是单纯的 CI/CD 工具，而是全链路研发平台。

### 六大核心模块

| 模块      | 能力                             |
| ------- | ------------------------------ |
| 代码托管    | Git 协作、合并请求（MR/PR）             |
| 云原生构建   | 声明式流水线，大仓友好（百 G 仓库秒克隆）         |
| 云原生开发   | 一键秒开云端容器开发环境                   |
| 制品库     | 制品管理、版本控制                      |
| AI 代码助手 | 智能补全、AI 代码评审、智能问答（接入 DeepSeek） |
| 任务集     | 看板式任务进度追踪                      |

**核心配置文件**：`.cnb.yml`，放在代码仓库根目录的声明式 YAML，定义整条流水线（Pipeline as Code，可跨仓引用，Git 管理追溯）。

### CNB vs Jenkins 核心区别（8 维度）

| 维度    | CNB 云原生构建                      | Jenkins                       |
| ----- | ------------------------------ | ----------------------------- |
| 配置方式  | 声明式 YAML（.cnb.yml，与代码同源）       | 命令式 Groovy（Jenkinsfile，门槛高）   |
| 基础设施  | Serverless 全托管，无需维护服务器，弹性伸缩    | 需自建自运维 Master/Agent 架构        |
| 构建环境  | Docker 镜像声明式指定，环境与资源解耦         | Agent 节点预装，手动配置，易漂移           |
| 缓存能力  | 百 G 缓存秒级准备（AOSP 编译 1h+ → 2min） | 本地缓存有限，需额外配分布式缓存              |
| 功能范围  | 全链路一体化（代码+CI/CD+制品+开发+AI）      | 仅 CI/CD 引擎，需集成 GitLab/Nexus 等 |
| 运维成本  | 零运维，按量计费，SaaS 开箱即用             | 高（升级、插件、安全补丁）                 |
| 扩展性   | 资源池化、高并发、大仓百 G 秒克隆             | 需手动加 Agent 节点，扩展受限            |
| AI 能力 | 原生集成（AI 评审 + 智能问答 + 补全）        | 无原生 AI，依赖第三方插件                |

### 本质区别

> **CNB 是云原生时代的声明式全链路开发者平台；Jenkins 是传统时代的命令式 CI/CD 引擎。**  
> CNB 把「环境在哪、资源多少、缓存怎么管」的复杂性全部屏蔽，开发者只声明意图；Jenkins 需亲手搭建维护整个执行基础设施。

### 客观补充

Jenkins 生态成熟（1800+ 插件）、私有化可控性强，已有完善 Jenkins 基建且对数据完全私有化有强要求的团队仍有其价值。CNB 更适合轻量起步、追求云原生体验、不想投入基础设施运维的团队。

### 版本

- **社区版**：SaaS 开箱即用，微信扫码注册，适合公网/开源协作。
- **企业版**：部署至指定腾讯云 VPC，数据存储自管理、网络策略自定义，适合企业内网。

- 见 Q3：CNB 如何与 TKE 集成实现自动构建部署（镜像存 CNB 制品库）。

## Q2（2026-08-06）：.cnb.yml 如何配置流水线？给一个 Java 项目构建部署示例。

### 一句话理解

CNB 的流水线由仓库根目录的 `.cnb.yml`（声明式 YAML）定义。整体是「**触发分支 → 触发事件 → 流水线(Pipeline) → 阶段(Stage) → 任务(Job)**」五层结构，每一步用 Docker 镜像指定运行环境，用 `script` 写执行命令。

### 层级结构

```
触发分支(main / dev / feature/* / $ 兜底)            ← 哪些分支触发
  └─ 触发事件(push / pull_request / tag_push)        ← 什么操作触发
       └─ Pipeline 流水线(可多条, name 唯一)          ← 一次完整构建
            └─ stages 阶段(依次执行)                  ← 构建步骤分组
                 └─ jobs 任务(script 或插件)          ← 最小执行单元
```

### 最小可用示例

```yaml
main:                      # 触发分支
  push:                    # 触发事件：推送到 main 时
    - docker:              # 流水线执行环境（可指定任意 Docker 镜像）
        image: node:22
      stages:
        - name: install
          script: npm install
        - name: test
          script: npm test
```

要点：配置文件即代码，随仓库走 Git 版本管理，可走 PR 评审变更。

### Java 项目「构建 → 测试 → 打镜像 → 推 TCR → 部署 TKE」完整示例

```yaml
# .cnb.yml —— Java (Maven) 构建并部署到 TKE
main:
  push:
    - name: build-deploy
      stages:
        # 1) 编译打 jar
        - name: build
          image: maven:3.9-eclipse-temurin-17
          script: |
            mvn -B clean package -DskipTests

        # 2) 跑单元测试
        - name: test
          image: maven:3.9-eclipse-temurin-17
          script: |
            mvn test

        # 3) 打 Docker 镜像并推送到腾讯云容器镜像服务 TCR
        - name: docker-build-push
          image: docker:24
          services:
            - docker            # 开启 docker-in-docker
          script: |
            docker build -t ccr.ccs.tencentyun.com/saas/myapp:${CNB_COMMIT} .
            docker push ccr.ccs.tencentyun.com/saas/myapp:${CNB_COMMIT}

        # 4) 部署到 TKE（更新 UAT 命名空间下的 deployment 镜像）
        - name: deploy
          image: bitnami/kubectl:latest
          script: |
            kubectl set image deployment/myapp \
              myapp=ccr.ccs.tencentyun.com/saas/myapp:${CNB_COMMIT} -n saas-uat

      # 失败兜底：任一阶段失败执行通知
      failStages:
        - name: notify
          script: echo "流水线失败，请检查 CNB 构建日志"
```

> 说明：镜像仓库用 `ccr.ccs.tencentyun.com`（TCR 域名按实际填写）；`${CNB_COMMIT}` 为 CNB 内置变量（提交 ID），用于镜像版本唯一化，便于回滚。

### 关于「部署到 TKE」与你的操作偏好

- CNB 里的部署步骤本质是一段 `script`（这里是 `kubectl`，属于**排障/部署必会命令**，已标注）。
- 若更想走**控制台 UI**：可让 CNB 只负责「构建 + 推镜像」，最后一步部署改在 TKE 控制台手动「更新镜像」完成（CNB 不写 kubectl）。
- 凭据（TCR 登录、kubeconfig）通过 CNB 的 **Secret 变量 / Secret 仓库**注入（`imports:` 引用），不要明文写在 `.cnb.yml` 里。

### 关键配置项速查（Pipeline 级）

| 配置项                                   | 作用                                      |
| ------------------------------------- | --------------------------------------- |
| `docker.image`                        | 指定流水线/任务运行的 Docker 镜像（构建环境）             |
| `runner`                              | 构建节点规格（tags、cpus 资源大小）                  |
| `services`                            | 构建伴随服务，如 `docker`（dind）、`vscode`（云原生开发） |
| `env` / `imports`                     | 环境变量；`imports` 从其他仓库文件导入 Secret         |
| `git`                                 | 仓库行为（enable、submodules、lfs）             |
| `stages` / `failStages` / `endStages` | 主流程 / 失败流程 / 收尾流程                       |
| `retry` / `allowFailure`              | 失败重试次数 / 允许失败不阻断                        |
| `lock`                                | 流水线锁，防并发冲突                              |
| `sandbox`                             | 沙箱模式                                    |

## Q3（2026-08-06）：CNB 如何与 TKE 集成，实现代码提交后自动构建镜像并部署到容器集群？

### 一句话理解

把「代码 push → CNB 触发 `.cnb.yml` → Maven 构建 → 打镜像推 **CNB 制品库** → 部署 TKE」串成一条自动流水线。镜像直接存 CNB 自带的 Docker 制品库（`docker.cnb.cool`），**流水线内免 docker login**；再经官方 `tencentcom/deploy-to-tke` 插件免 kubectl 更新 TKE 工作负载。全程在一个平台内闭环。

### 整体链路

```
开发者 push 代码
   │
   ▼
CNB 监听 .cnb.yml（main 分支 push 触发）
   │
   ├─ stages: Maven 构建 jar
   ├─ stages: docker build → 推送 CNB 制品库（docker.cnb.cool/${CNB_REPO_SLUG_LOWERCASE}）
   │
   ▼
部署 TKE（见下，镜像均来自 CNB 制品库）
   ├─ 路径A：CNB 插件 tencentcom/deploy-to-tke 直接更新工作负载镜像
   └─ 路径B：TKE 控制台手动「更新镜像」指向 CNB 制品库地址（需配 imagePullSecret）
   │
   ▼
TKE 集群滚动更新 Pod（K8s 异步调度，支持回滚）
```

### CNB 制品库（Docker 制品）要点

- 仓库地址：`docker.cnb.cool`
- 路径规则：
  - 同名制品：`docker.cnb.cool/${CNB_REPO_SLUG_LOWERCASE}`
  - 非同名制品：`docker.cnb.cool/${CNB_REPO_SLUG_LOWERCASE}/<制品名>`
- 内置变量：`${CNB_DOCKER_REGISTRY}`（即 `docker.cnb.cool`）、`${CNB_REPO_SLUG_LOWERCASE}`（仓库路径小写）、`${CNB_COMMIT}`（提交 ID）
- **关键优势**：在 CNB 流水线内推送镜像**无需 `docker login`**，平台已自动鉴权；凭据不进代码，也**不必额外维护 TCR 登录 Secret**。
- 本地手动推送需：`docker login docker.cnb.cool -u cnb -p ${CNB_TOKEN}`（CNB 访问令牌）。

### 方式一：CI 构建并自动部署（push 触发，用官方插件）

> 每次 push 都部署，适合开发/测试环境。生产环境建议方式二。

```yaml
# .cnb.yml
main:
  push:
    - name: build-and-deploy
      services:
        - docker                       # 开启 docker-in-docker
      imports:
        - https://cnb.cool/your-group/your-secret-repo/-/blob/main/tke_secrets.yml   # 注入 TKE API 密钥
      stages:
        # 1) Maven 构建
        - name: build
          image: maven:3.9-eclipse-temurin-17
          script: mvn -B clean package -DskipTests

        # 2) 打镜像并推送到 CNB 制品库（流水线内免 docker login）
        - name: docker-build-push
          image: docker:24
          script: |
            docker build -t ${CNB_DOCKER_REGISTRY}/${CNB_REPO_SLUG_LOWERCASE}:${CNB_COMMIT} .
            docker push ${CNB_DOCKER_REGISTRY}/${CNB_REPO_SLUG_LOWERCASE}:${CNB_COMMIT}

        # 3) 用 CNB 官方插件直接更新 TKE 工作负载（免 kubectl，拉取 CNB 制品库镜像）
        - name: deploy-to-tke
          image: tencentcom/deploy-to-tke
          settings:
            secret_id: ${SECRET_ID}          # 来自 tke_secrets.yml
            secret_key: ${SECRET_KEY}
            region: ap-guangzhou
            cluster_id: cls-xxxxxxxx         # TKE 集群 ID
            namespace: saas-uat
            workload_kind: deployment
            workload_name: myapp
            container_names: myapp
            container_images: ${CNB_DOCKER_REGISTRY}/${CNB_REPO_SLUG_LOWERCASE}:${CNB_COMMIT}
```

**TKE 拉取 CNB 制品库镜像**：若制品库为私有，需在 TKE 侧配置 `docker.cnb.cool` 的 `imagePullSecret`（对应 CNB 访问令牌），否则集群拉不到镜像；公开制品库无需此步。

**密钥文件**（放 CNB Secret 仓库，不进代码）：

```yaml
# tke_secrets.yml
SECRET_ID: AKIDxxxxxxxxxxxxxxxx
SECRET_KEY: xxxxxxxxxxxxxxxxxxxx
allow_slugs: your-group/your-repo        # 仅允许指定仓库引用
allow_images: tencentcom/deploy-to-tke   # 仅允许该插件引用
```

### 方式二（推荐生产）：按环境部署流程，支持多环境/审批

用 `.cnb/tag_deploy.yml` 定义部署环境，对 `tag_push` 触发，可配置多环境、审批、前置条件。镜像同样来自 CNB 制品库。比「每次 push 都部署」更适合生产，避免误推即上线。

### 方式三（偏控制台）：TKE 手动「更新镜像」

- CNB 流水线只负责「构建 + 推镜像到 CNB 制品库」。
- 在 **TKE 控制台**手动「更新镜像」，地址填 `docker.cnb.cool/...:${CNB_COMMIT}`（配合 `imagePullSecret`）。
- 优点：部署动作完全在控制台点击，CNB 里无需任何部署代码 / `kubectl`。

### 与你的操作偏好对应

| 部署方式                 | 镜像存哪    | 写 kubectl？   | 偏 UI？ | 适用      |
| -------------------- | ------- | ------------ | ----- | ------- |
| 官方插件 `deploy-to-tke` | CNB 制品库 | 否（参数化）       | 中     | 自动化部署   |
| TKE 控制台手动更新          | CNB 制品库 | 否            | 是     | 想尽量少碰命令 |
| kubectl apply（见 Q2）  | 任意      | 是（**必会/排障**） | 否     | 排障、精细控制 |

> 注：若团队已用 TCR，仍可沿用「TCR 触发器联动 TKE」；但本次约定镜像**直接存 CNB 制品库**，走上方方式一/二/三即可，省去 TCR 登录凭据维护。

### 关联

## Q4（2026-08-06）：TKE 容器服务是什么？与自建 Kubernetes 集群相比有什么优势？

### 一句话理解

**TKE（Tencent Kubernetes Engine，腾讯云容器服务）是腾讯云提供的托管式 Kubernetes 服务**——基于原生 K8s，把「控制平面（Master/etcd）+ 一部分节点运维」交给腾讯云托管，深度集成云上网络、存储、负载均衡、监控等能力，让你专注跑应用，而不是养集群。

### TKE 是什么

- 基于原生 Kubernetes，提供以**容器为核心的企业级容器管理服务**，覆盖部署运行、资源调度、服务发现、动态伸缩。
- 你**无需安装部署集群管理基础设施**，只需简单 API 调用即可启动/停止容器化应用；复杂的集群管理工作（控制面 HA、升级、安全补丁）由腾讯云完成。
- 官方定位：高度可灵活扩展的高性能容器管理服务，让你在云服务器实例集群上轻松运行 Docker 应用。

### TKE 的集群/节点形态（理解形态，便于对号入座）

| 形态                   | 说明                        | 适合              |
| -------------------- | ------------------------- | --------------- |
| 标准集群                 | 用户管理 Worker 节点（CVM），控制面托管 | 绝大多数业务，掌控节点     |
| Serverless 集群 / 超级节点 | 无需管理节点，按 Pod 资源用量计费       | 极致弹性、免运维、波峰波谷明显 |
| 边缘集群                 | 面向边缘计算场景                  | 边缘/IoT          |
| 原生节点（Housekeeper 模式） | 腾讯云自研节点管理，高稳定快响应          | 追求资源效能/装箱率      |
| 注册节点                 | 纳管 IDC 等自有资源              | 混合云/存量机器        |

> 你的练手/测试环境用的就是「标准集群 + 普通节点」，本质 Worker 节点跑在 CVM 上。

### TKE vs 自建 Kubernetes（核心维度对比）

| 维度                   | TKE 托管                                 | 自建 K8s                           |
| -------------------- | -------------------------------------- | -------------------------------- |
| **控制面（Master/etcd）** | 腾讯云全托管，保障高可用、安全、自动升级                   | 需自建 3 Master + etcd 高可用，自己管升级与容灾 |
| **节点运维**             | 节点池 / 托管节点池 / 超级节点，一键扩缩、自动修复           | 自行管理节点生命周期、kubelet 升级、OS 补丁      |
| **网络**               | VPC-CNI：Pod 直接拿 VPC IP，与 CVM 网络对等      | 需自选 CNI 插件并自行运维，跨网络互通要自己打通       |
| **存储**               | CBS 云硬盘动态卷供应（Dynamic Provisioning）开箱即用 | 需部署 CSI 驱动、对接存储后端                |
| **负载均衡**             | Service 自动绑定 CLB，流量自动增减后端              | 需自建/集成 LB，手动维护后端                 |
| **可观测性**             | 原生集成云监控 + CLS 日志，多层级监控告警               | 需自建 Prometheus + 日志栈             |
| **权限/多租户**           | CAM 账号/命名空间级权限隔离                       | 需自建 RBAC + 外部鉴权                  |
| **高可用**              | 跨可用区（AZ）部署 + 反亲和，故障自动恢复                | 需自行设计跨 AZ 容灾方案                   |
| **成本**               | 省 Master 资源 + 运维人力（控制面通常免节点费，仅少量集群管理费） | 要养 Master 节点 + 专职 K8s 运维人力       |

### 关键优势展开

1. **控制面零运维**：API Server / Scheduler / Controller Manager / etcd 由腾讯云保障高可用、安全、升级——这是自建 K8s 里最重、最易出事的环节（etcd 数据损坏、证书过期、版本升级翻车都是经典坑）。
2. **与云产品深度集成，开箱即用**：CLB（自动绑 Service）、CBS（动态存储卷）、VPC-CNI（高性能容器网络）、云监控、CLS 日志——自建要一项项自己接，链路长、坑多。
3. **弹性与自动化**：节点池弹性伸缩、托管节点池自动修复异常节点、超级节点秒级扩容到很大规格，无需人工判断容量。
4. **企业级能力内置**：命名空间级资源隔离、灰度/蓝绿发布、集群巡检、不停机升级，省去自研或拼装。
5. **降本**：省掉 Master 节点的计算资源开销，更省专职 K8s 运维的人力成本；配合 Crane 调度（节点放大、碎片规整、在离线混部）还能把装箱率/资源利用率再拉高。

### 客观补充：什么时候仍可能选自建

- 数据/合规要求**完全不能出私有环境**，且需要底层完全自定义的（但腾讯云也有私有化版本 TCE / TKE 企业版可部署到自有 IDC）。
- 已有成熟 K8s 运维团队与完整工具链，且对特定内核/网络有强定制需求。
- 绝大多数中小团队、追求云原生体验、不想养 K8s 基础设施的，**TKE 托管是更省心的选择**。

### 与前面内容的关联

- 见 Q2 / Q3：CNB 流水线最终部署的目标就是 **TKE 集群**（用 `deploy-to-tke` 插件或 kubectl 更新 TKE 工作负载）。
- 你公司的 TKE 应用与网关对象就跑在这种托管集群上——理解「控制面托管、节点池弹性、VPC-CNI 网络」是后续排查 Pod 调度、网络、镜像拉取问题的基础。
- 后续可深入：TKE 控制台创建集群实操、节点池 vs 超级节点选型、`imagePullSecret` 配 CNB 制品库私有镜像、HPA 弹性伸缩、K8s 排障命令（kubectl 必会）。

## Q5（2026-08-06）：如何在 TKE 上快速创建一个 Nginx 容器服务？完整操作步骤

> 默认走**控制台 UI 点击**步骤（符合你的操作偏好）。kubectl 命令附在末尾作**排障/对照**用。

### 前置条件

- 已有一个 TKE 集群（标准集群即可，控制面托管，Worker 节点就绪）。
- 集群安全组需放通：节点网络、容器网络，以及端口 **30000–32768**（否则 Service 可能不可用）。

### 控制台操作步骤（8 步）

1. **进入集群**：TKE 控制台 → 左侧「集群」→ 点击目标集群的「ID/名称」进入集群详情。
2. **新建工作负载**：左侧「工作负载」→「Deployment」→ 点击「新建」。
3. **基本信息**：工作负载名称填 `nginx`；命名空间选 `default`（或自建）；标签默认 `k8s-app=nginx`。
4. **实例内容器**：
   - 名称：`nginx`（自定义）
   - 镜像：点「选择镜像」→ 选 `nginx`（或填 `nginx`，Tag 用 `latest`）
   - 镜像拉取策略：默认 `IfNotPresent` 即可
   - （可选）CPU/内存「资源限制」：如请求 0.25 核 / 256Mi，上限 0.5 核 / 512Mi
5. **实例数量**：选「手动调节」，实例数填 `1`（或选「自动调节」交给 HPA，见 Q7）。
6. **访问设置（Service）**：
   - 勾选「启用」Service
   - 服务访问方式：选「**公网 LB 访问**」（LoadBalancer，自动创建 CLB）
   - 端口映射：协议 TCP，容器端口 `80`、服务端口 `80`
7. **确认创建**：点击「创建 Deployment」，等待 Pod 状态变为 Running。
8. **访问验证**：左侧「服务与路由」→「Service」→ 复制该 Nginx 服务的「负载均衡 IP（CLB IP）」→ 浏览器打开 `http://<CLB_IP>`，看到 Nginx 欢迎页即成功。

> 集群内其他服务可用「服务名 + 80 端口」直接互访（如 `nginx.default.svc.cluster.local:80`）。

### 排障/对照：kubectl 写法（**必会/可选**）

```bash
# 部署
kubectl create deployment nginx --image=nginx:latest -n default
kubectl expose deployment nginx --port=80 --type=LoadBalancer
# 查看
kubectl get deploy,pods,svc -n default
kubectl get svc nginx -n default   # EXTERNAL-IP 即 CLB 公网 IP
```

> 注：`type: LoadBalancer` 在 TKE 会**自动创建 CLB**（默认基于 NodePort 绑定节点）。默认免费额度按账号配额，超出按 CLB 计费。

### 关联

- 见 Q6：Service 的三种访问方式（ClusterIP / NodePort / LoadBalancer）与 Ingress 七层转发。
- 见 Q4：你部署的对象就跑在这类 TKE 托管集群的 Deployment 上。

## Q6（2026-08-06）：TKE 集群的网络模型是什么样的？Service 和 Ingress 分别怎么用？

### TKE 网络模型（CNI 方案）

TKE 提供三种容器网络 CNI，核心决定「Pod 的 IP 从哪来、怎么互通」：

| CNI 方案             | 原理                                                              | 适用                      |
| ------------------ | --------------------------------------------------------------- | ----------------------- |
| **VPC-CNI（推荐公有云）** | 基于 VPC 弹性网卡(ENI)，直接把 ENI 的 IP 分给 Pod，Pod 与节点同一网络平面，IP 在 VPC 网段内 | 对时延/性能敏感、需固定 Pod IP 的业务 |
| **Global Router**  | 基于网桥 + VPC 全局路由，Pod 网段独立于 VPC，跨节点 Pod 靠全局路由转发                   | 大规模、IP 需求充裕、扩展性优先       |
| **Cilium-Overlay** | 基于 Cilium VXLAN                                                 | 注册节点（纳管 IDC）场景          |

- **VPC-CNI 优**：性能比 Global Router 高约 10%、可复用 VPC 能力（EIP/安全组/CLB）、支持 Pod 固定 IP；有「共享 ENI」（高密度，支持固定 IP）和「独占 ENI」（单 Pod 独占网卡，高吞吐低延迟）两种模式。
- **Global Router 优**：容器网段地址充裕、扩展性强、适配大规模业务。
- 选型建议：公有云默认选 **VPC-CNI**；不确定时可建 Global Router 集群再按需开启 VPC-CNI 混用。

### Service（四层 / L4）：把 Pod 暴露为稳定访问入口

Service 给一组 Pod 一个固定虚拟 IP + DNS 名，屏蔽 Pod 扩缩容/重建带来的 IP 变化。三种类型：

| 类型               | 访问范围                    | 说明                              |
| ---------------- | ----------------------- | ------------------------------- |
| **ClusterIP**    | 仅集群内                    | 默认类型，集群内服务互访                    |
| **NodePort**     | 节点 IP + 端口(30000–32768) | 节点 IP 暴露，测试用                    |
| **LoadBalancer** | 公网/内网（自动创建 CLB）         | TKE 生产常用；默认后端绑节点 NodePort，经一层转发 |

> TKE 的 LoadBalancer 默认实现：CLB 绑定各节点 NodePort 作后端 → 流量到节点后再经 kube-proxy(ipvs/iptables) 转发到 Pod。VPC-CNI 模式下可用「**CLB 直通 Pod**」省掉 NodePort 这一跳，性能更好。

### Ingress（七层 / L7）：按域名/URL 路由

- Ingress 做 **HTTP/HTTPS 七层转发**：一个 CLB + 80/443 监听器，按域名和 URL path 把流量分到不同 Service。
- TKE 自带默认 Ingress 控制器（基于 CLB）。你在「服务与路由 → Ingress」新建规则：填域名、路径、后端 Service + 端口即可。
- 典型用法：一个公网 CLB 同时承载 `a.example.com` → service-a、`b.example.com/api` → service-b。
- 配合 HTTPS 可在 Ingress 配置证书做 SSL 卸载。

### Service vs Ingress 怎么选

| 场景                         | 用                      |
| -------------------------- | ---------------------- |
| 集群内服务互访                    | ClusterIP              |
| 单个服务直接对公网/内网暴露（TCP/UDP 四层） | LoadBalancer           |
| 多域名/多路径、七层路由、SSL 卸载、统一入口   | Ingress（后端仍指向 Service） |

### 关联

- 见 Q5：Nginx 示例用的就是 LoadBalancer 类型 Service。
- 见 Q4：VPC-CNI 是 TKE 网络基础，影响 Pod IP、网络性能、安全组策略。

## Q7（2026-08-06）：TKE 的节点池是什么？如何实现集群的弹性伸缩？

### 节点池是什么

**节点池（Node Pool）** 是对集群内一组**相同属性节点**的分组管理单元。同一节点池内的节点共享：

- 节点操作系统、计费类型（按量/竞价/包年包月）
- CPU/内存/GPU 规格
- kubelet 启动参数、自定义启动脚本
- Kubernetes Label / Taint

用途：大规模集群下规范节点分组、频繁扩缩容、按标签调度、批量升级 Docker/k8s 版本。一个节点池对应腾讯云**一个伸缩组（ASG）**，你只需关心节点池。

### 弹性伸缩的两层模型

TKE 弹性伸缩分两层，**通常组合使用**：

| 层              | 组件                                 | 扩什么 | 触发依据                              |
| -------------- | ---------------------------------- | --- | --------------------------------- |
| **Pod 层（应用层）** | **HPA**（Horizontal Pod Autoscaler） | 副本数 | CPU/内存/磁盘/网络/GPU 等指标，或自定义指标（QPS）  |
| **节点层（资源层）**   | **CA**（Cluster Autoscaler）         | 节点数 | Pod 因资源不足 Pending 时自动加节点；节点空闲自动回收 |

> 协同逻辑：流量涨 → HPA 加 Pod → 若现有节点资源不够 → CA 扩节点池 → Pod 被调度；流量落 → HPA 减 Pod → 节点空闲 → CA 缩节点。

### 控制台开启步骤

**① 开启节点池弹性伸缩（CA）**

1. 集群 →「节点管理」→「节点池」→ 新建节点池（或选已有）。
2. 节点池设置：机型、计费、最小/最大节点数、期望节点数。
3. 开启「**Cluster Autoscaler**」开关（前提：集群至少有一个状态正常的节点池）。
4. 触发条件：默认「资源不足无法调度的 Pod（PodScheduled=False）」即扩容；可设「触发扩容资源阈值」（如 70%）提前扩。

**② 配置 HPA（Pod 自动扩缩）**

1. 工作负载 → 选 Deployment →「自动伸缩」→ 新建 HPA。
2. 指标选 CPU 使用率（如目标 50%），设置最小/最大副本数。
3. 保存后，HPA 持续监控指标自动调副本。

**③（可选）定时扩缩**

- TKE 自研 **HPC**（Horizontal Pod CronScaler）：用 Cron 语法在可预期高峰前提前扩副本（如游戏周五晚扩容、周日晚缩容），弥补 HPA「等监控再反应、不够快」的短板。在「扩展组件」页安装后使用。

### 排障/对照：kubectl 写法（**必会/可选**）

```bash
# 查看 HPA 状态
kubectl get hpa -n default
kubectl describe hpa <name> -n default
# 查看节点池相关事件 / Pod 为何 Pending
kubectl get pods -n default
kubectl describe pod <pending-pod>   # 看 Events 里是否 "FailedScheduling: Insufficient cpu/memory"
```

> 注意：CA 用 workload 的 **Request 值**计算资源，而非真实使用率——所以给 Pod 设合理的 resources.requests 是弹性伸缩能正确触发的前提。

### 关联

- 见 Q5：实例数量选「自动调节」即对应 HPA 入口。
- 见 Q4：节点池/超级节点是 TKE 弹性的载体，省去自建 K8s 手工加节点的运维。

## Q8（2026-08-06）：TKE 中如何配置持久化存储？PV 和 PVC 在 TKE 中的使用方法是什么？

### 核心概念（标准 K8s + TKE 默认集成）

- **PV（PersistentVolume）**：集群级存储资源（类似节点），生命周期独立于 Pod。TKE 中 PV 底层是云硬盘（CBS）。
- **PVC（PersistentVolumeClaim）**：对存储的「请求」（类似 Pod 申请节点资源）。PVC 不足时系统按 StorageClass **动态创建** PV。
- **StorageClass**：存储「类别模板」，管理员定义不同存储规格；TKE **默认提供块存储(CBS) 的 StorageClass**（名称一般为 `cbs`，provisioner `com.tencent.cloud.csi.cbs`）。

### 控制台操作步骤（动态供给，最常用）

1. **新建 StorageClass**（可选，默认 `cbs` 已够用）：
   - 集群 →「存储」→「StorageClass」→「新建」
   - 参数：名称 `cbs-test`、providers 选「云硬盘 CBS」、可用区、云盘类型（高性能/SSD/增强型 SSD）、回收策略（**建议 Retain 保数据**）、计费（按量/包月）、可选「在线扩容」。
2. **新建 PVC**：
   - 「存储」→「PersistentVolumeClaim」→「新建」
   - 名称 `cbs-pvc`、命名空间、Provisioner 选 CBS、**读写权限（CBS 仅支持单节点读写 RWO）**、StorageClass 选上面建的、容量（如 10Gi）。
   - 保存后系统自动创建对应 PV（CBS 云盘）。
3. **工作负载挂载 PVC**：
   - 新建/编辑 Deployment →「数据卷」→「添加数据卷」→「使用已有 PVC」→ 选 `cbs-pvc`。
   - 在容器「挂载点」里把这卷挂到容器路径（如 `/usr/share/nginx/html`）。
   - 创建后 Pod 内该路径即持久化到 CBS，Pod 重建数据不丢。

### 排障/对照：kubectl 写法（**必会/可选**）

```bash
# 查看
kubectl get sc          # 看 StorageClass（默认 cbs）
kubectl get pvc -n default
kubectl get pv
# 用已有 CBS 云盘手动建 PV（示例）
cat <<'EOF' | kubectl apply -f -
apiVersion: v1
kind: PersistentVolume
metadata:
  name: nginx-pv
spec:
  capacity:
    storage: 10Gi
  accessModes: [ReadWriteOnce]
  storageClassName: cbs
  qcloudCbs:
    cbsDiskId: disk-xxxxxxx   # 已有 CBS 盘 ID
    fsType: ext4
EOF
```

### 重要注意事项

- **CBS 块存储仅支持单节点读写（RWO）**：一个 PVC 同一时刻只能挂一台 Node 上的一个 Pod，不能多副本共享。
- **不支持跨可用区挂载**：挂了 CBS PV 的 Pod 若漂到别的可用区会挂载失败——多可用区部署需用**拓扑感知**或改用共享存储。
- **共享存储用 CFS（文件存储）**：需要多 Pod 同时读写（RWX，如多个 Nginx 共享静态资源）时，用腾讯云 CFS（NFS），对应 StorageClass 类型不同。
- 控制台默认 `cbs` StorageClass 即块存储；在线扩容需在 StorageClass 开 `allowVolumeExpansion: true`（控制台勾「在线扩容」）。

### 关联

- 见 Q5/Q6：有状态/需落盘的应用（如数据库、上传目录）才需要 PVC，无状态 Web（Nginx）一般不挂持久卷。
- 见 Q4：持久化存储是 TKE 深度集成云产品（CBS）的典型能力，自建 K8s 要自己接 CSI。

## Q9（2026-08-06）：腾讯云云原生网关是什么？它和传统 CLB 负载均衡有什么核心区别？

### 云原生网关是什么

**云原生网关（TSE 微服务引擎里的「云原生 API 网关」）** 是腾讯云基于开源微服务网关（**Kong / Spring Cloud Gateway 内核**，100% 兼容开源）推出的**托管 API 网关**。它是微服务/容器架构的**业务层流量入口**，在转发流量的同时提供：请求分发、API 管理、限流熔断、流量灰度、鉴权、IP 黑白名单、可观测与链路追踪等能力。

- 由腾讯云托管（免运维、多可用区容灾、不停服扩缩容），轻松应对百万并发。
- 原生支持 K8s/容器与微服务生态，可对接 TKE、注册中心（如北极星 Polaris）等。

### 与 CLB 的核心区别

| 维度     | 云原生网关（API 网关）                     | CLB 负载均衡                    |
| ------ | --------------------------------- | --------------------------- |
| 工作层级   | **应用层（L7+，业务语义）**                 | 网络层（L4 四层 / L7 七层转发）        |
| 内核     | Kong / Spring Cloud Gateway（开源网关） | TGW（四层）/ STGW（七层，自研 Nginx）  |
| 核心职责   | **API 治理**：路由、限流、鉴权、灰度、可观测        | **流量分发**：把请求转发到后端、负载均衡、健康探测 |
| 是否理解业务 | 是（识别域名/路径/Header/API，能做业务规则）      | 仅做转发，不解析业务语义                |
| 典型角色   | 业务入口/API 网关，常位于 CLB 之后            | 流量接入/负载均衡，最外层入口             |
| 适用     | 微服务、API 管理、需限流鉴权灰度的场景             | 任意需要高可用负载均衡对外/对内暴露的服务       |

> 本质区别：**CLB 是「把流量送到哪台机器」的管道；云原生网关是「按什么业务规则处理请求」的治理层。** 常见架构是「外部 → CLB（接入/负载）→ 云原生网关（业务治理）→ 后端服务」。

### 注意（开通范围）

云原生网关目前主要面向**微服务场景**（作为北极星 Polaris 服务接入层）开通白名单新购；其余场景控制台会重定向至北极星控制台。如有新购需求需提交工单。（这是产品当前策略，实际以控制台可见性为准。）

### 关联

- 见 Q10/Q11：云原生网关实例怎么建、路由怎么指、插件怎么配。
- 见 Q12：CLB 的四层/七层转发能力。
- 见 Q17：三者（CLB / NAT / 云原生网关）在流量入口场景的选型。

## Q10（2026-08-06）：如何创建云原生网关实例，并将路由指向 TKE 集群内的服务？

> 控制台步骤（TSE 微服务引擎控制台）。以下以「网关后端指向 TKE 集群内的 Service」为例。

### 控制台操作步骤

1. **进入控制台**：腾讯云控制台 → 搜索「微服务引擎 TSE」→「云原生网关」→「新建实例」。
2. **创建网关实例**：
   - 名称、规格（节点数/实例规格，按流量选）、**所属 VPC、子网、可用区**（建议与后端 TKE 集群同 VPC 或打通）。
   - 确认计费，创建后等待实例「运行中」。
3. **配置服务来源（后端发现）**：
   - 网关实例详情 →「服务来源」→「新建」。
   - 类型选 **Kubernetes（TKE）**，关联你的 TKE 集群（选集群、命名空间），网关会自动发现该集群内的 Service 作为可路由后端。
   - （也支持 Polaris、注册中心、IP 列表等其他来源。）
4. **创建路由**：
   - 「路由管理」→「新建路由」。
   - 匹配规则：域名（如 `api.example.com`）、路径（如 `/`，或 `/order/**`）、协议 HTTP/HTTPS。
   - 后端服务：选第 3 步发现的 TKE Service + 端口（如 `myapp:8080`）。
   - 可配多后端做灰度（见 Q11）。
5. **获取网关访问地址**：实例详情有网关的访问 VIP/域名，可前置 CLB 或直接解析你的业务域名到该地址。
6. **验证**：`curl http://<网关地址>/` 应返回后端 TKE 服务的响应。

### 排障/对照（**必会/可选**）

```bash
# 确认 TKE 内目标服务存在且端口正确（网关后端才能被发现）
kubectl get svc -n <命名空间>        # 看 Service 名、CLUSTER-IP、端口
kubectl get endpoints -n <命名空间>   # 看 Service 后端 Pod 是否就绪
```

> 若网关看不到服务：检查 TKE 集群与网关是否同 VPC/网络互通，命名空间是否选对，Service 是否 Ready。

## Q11（2026-08-06）：云原生网关支持哪些插件（限流、鉴权、灰度等）？如何配置？

### 支持的插件类型（开箱即用 + 开源生态）

| 类别        | 插件举例                                         | 作用                 |
| --------- | -------------------------------------------- | ------------------ |
| **限流熔断**  | 限流（rate limiting，令牌桶/漏桶）、熔断（circuit breaker） | 防突发流量打垮后端、异常实例快速失败 |
| **鉴权安全**  | key-auth、JWT、OAuth2、basic-auth、IP 黑白名单       | 校验调用方身份、拦截非法来源     |
| **灰度/发布** | 金丝雀(canary)、按权重/Header/域名分流、流量镜像             | 按比例或按规则切流，灰度验证新版本  |
| **流量治理**  | 重写(rewrite)、重定向(redirect)、CORS、重试/超时         | 路径改写、跨域、容错         |
| **可观测**   | 监控、日志（CLS）、链路追踪（APM）                         | 看 QPS/延迟/错误率、定位慢调用 |

> 内核兼容开源 Kong，因此**社区插件和自定义插件**也可用，扩展性强。

### 配置方式（控制台）

- 在「**插件管理**」或具体「路由/服务」上**绑定插件策略**，按作用范围分：全局 / 服务级 / 路由级。
- **限流示例**：路由 → 添加「限流」插件 → 设 QPS 阈值（如 100/s）+ 限流维度（按 IP/按 API）。
- **鉴权示例**：开启「JWT」或「key-auth」插件 → 配置密钥/claim 校验；未带合法凭证的请求被拒。
- **灰度示例**：同一路由配两个后端（v1、v2），设权重 `v1:90% / v2:10%`；或按 Header（如 `x-version: canary`）精确切流；流量镜像可复制一份到新版本观察不影响生产。

### 关联

- 见 Q9/Q10：插件运行在云原生网关上，先有网关实例和路由再叠加插件。
- 见 Q17：限流/鉴权/灰度是「为什么选云原生网关而非纯 CLB」的关键理由。

## Q12（2026-08-06）：CLB 负载均衡支持哪几种转发模式？四层和七层分别适用什么场景？

### CLB 支持的协议/转发模式

CLB 一个实例上可配**监听器**，按协议分两类：

| 类别         | 协议                   | 转发依据                       |
| ---------- | -------------------- | -------------------------- |
| **四层（L4）** | TCP、UDP、TCP SSL、QUIC | **VIP + 端口**（传输层），透传不修改数据包 |
| **七层（L7）** | HTTP、HTTPS           | **域名、URL 路径、Header**（应用层）  |

### 四层（L4）特点与适用

- 基于 IP+端口转发，数据包**透传（不修改）**，转发效率极高；服务端能直接拿到**客户端真实 IP**；支持基于源 IP 的会话保持。
- 适用：**对可靠性/速度要求高、无需解析请求内容**的场景。
  - TCP：文件传输、邮件、远程登录、数据库连接。
  - UDP：即时通讯、音视频、游戏（低延迟、可丢包）。
  - TCP SSL：需 TCP 层加密/证书校验的自定义协议。

### 七层（L7）特点与适用

- 基于**域名/URL/Header** 做精细化分发；支持 Cookie 会话保持、SSL 卸载（统一证书管理）、内容路由（一个监听器多域名、一域名多路径）。
- 适用：**Web / 移动应用、需按域名或路径分流、需 HTTPS 卸载、需识别请求内容**的场景。
  - 一个七层监听器配多域名，一个域名配多条转发路径，把不同请求分到不同后端服务（如 `a.com` → svc-a，`b.com/api` → svc-b）。

### 四层 vs 七层 速选

| 需求                            | 选              |
| ----------------------------- | -------------- |
| 不关心内容、只要快、要真实客户端 IP           | 四层（TCP/UDP）    |
| 按域名/URL 分流、HTTPS 卸载、Cookie 保持 | 七层（HTTP/HTTPS） |
| 数据库/游戏/音视频等专用协议               | 四层             |
| 多业务共用一个 CLB 入口、按路径分服          | 七层             |

### 关联

- 见 Q5/Q6：TKE 中 `LoadBalancer` 类型 Service 默认由 CLB 实现（后端绑节点 NodePort）。
- 见 Q9：云原生网关的七层能力比 CLB 七层更偏业务治理。
- 见 Q14/Q17：CLB 是流量入站分发的主要组件。

## Q13（2026-08-06）：NAT 网关是什么？它和公网 CLB 在功能上有什么不同？

### NAT 网关是什么

**NAT 网关（NAT Gateway）** 是 VPC 与公网之间的**地址转换（NAT）服务**，核心是让 VPC 内资源**安全地访问 Internet，且不暴露私有 IP**。具备：

- **SNAT（源地址转换）**：让 VPC 内**多个无公网 IP 的 CVM** 通过 NAT 绑定的公网 IP **主动访问公网**（出方向）。转发出去时源 IP 变成 NAT 的公网 IP。
- **DNAT（目的地址转换）**：把公网 IP:端口映射到内网 IP:端口，使内网服务可被公网访问（入方向，类似反向代理，1 对 1）。
- 其他：网关流控、流量告警、共享带宽包、双机热备自动容灾（99.99% 可用）、最高千万级并发。

### 与公网 CLB 的核心区别

| 维度     | NAT 网关                                  | 公网 CLB                    |
| ------ | --------------------------------------- | ------------------------- |
| 主方向    | **出公网（SNAT）为主**，DNAT 为辅                 | **入站（公网→后端）** 流量分发        |
| 转发模型   | SNAT 多对一（多 CVM 共用一个公网 IP 出网）；DNAT 一对一映射 | **一对多**（一个 CLB 把流量分给多台后端） |
| 负载均衡   | 无（不做后端池调度/健康探测）                         | 有（加权轮询、健康检查、故障摘除）         |
| 典型用途   | 让无公网 IP 的后端**安全出网**（拉更新、调第三方）           | 让服务**对外高可用提供**，分摊流量       |
| 是否暴露后端 | 后端无公网 IP，外部无法直接访问                       | 对外暴露统一入口 IP，后端可仅内网        |

> 一句话：**NAT 解决「出去」(CVM 访问公网)，CLB 解决「进来」(公网访问 CVM 服务)。** 二者功能互补、不冲突，常一起用（见 Q14）。

### 关联

- 见 Q14：CLB + NAT 组合实现「既对外服务又安全出网」。
- 见 Q17：NAT 不是对外入口，选型时别和 CLB 混淆。

## Q14（2026-08-06）：如何通过「CLB + NAT 网关」实现云服务器既安全访问公网又能对外提供服务？

### 目标

让 CVM **不绑定公网 IP**（不留公网入口、更安全的姿势），同时：① 能对外提供服务（入站）② 能访问公网（出站，如拉取更新、调第三方 API）。

### 架构

```
公网用户 ──► [公网 CLB] ──► CVM（仅内网）
CVM（仅内网）──► [NAT 网关 SNAT] ──► 公网
```

- **入站**：公网 CLB 接收外部请求 → 转发到后端 CVM（CVM 仅内网 IP，外部无法直接打它）。
- **出站**：CVM 默认路由 `0.0.0.0/0` 指向 NAT 网关 → NAT 用 SNAT 经自己的公网 IP 访问公网。

### 控制台步骤

1. **建公网 CLB 并对外**：CLB 控制台 → 新建「公网」CLB → 配监听器（四层/七层）→ 绑定后端 CVM（内网 IP + 端口）+ 权重。外部访问 CLB 的公网 IP 即到服务。
2. **建 NAT 网关并出网**：
   - NAT 网关控制台 → 新建「公网 NAT 网关」→ 绑定 EIP（弹性公网 IP）。
   - 到该 NAT 所在 VPC 的**子网路由表**加路由：`目的端 0.0.0.0/0` → `下一跳类型 公网 NAT 网关` → `下一跳 该 NAT`。
   - 配 **SNAT 规则**：指定哪些子网/CVM 通过该 NAT 出公网（可指定 EIP）。
3. **安全组配合**：CVM 安全组放通入站（来自 CLB 的网段/端口）和出站（如 TCP 80/443）。
4. **验证**：
   - 入站：浏览器/ curl 访问 CLB 公网 IP → 返回服务。
   - 出站：登录 CVM `ping` / `curl` 公网地址 → 通（出网走 NAT）。

### 安全收益

- CVM **无公网 IP**：外部无法直连 SSH/入侵，攻击面只剩 CLB 入口。
- 出网受 NAT 管控（可限制出口 EIP、端口、带宽），入网受 CLB + 安全组管控，双向可控。

### 关联

- 见 Q12：CLB 四层/七层监听器配置。
- 见 Q13：NAT 的 SNAT/DNAT 与 CLB 的区别。
- 见 Q17：该组合是典型的「对外服务 + 安全出网」标准架构。

## Q15（2026-08-06）：云联网 CEN 是什么？它和 VPC 对等连接有什么区别？

### 云联网 CEN（CCN）是什么

**云联网（Cloud Connect Network, CCN）** 提供云上 **VPC 之间、VPC 与本地 IDC 之间**的**内网互联**服务，具备：全网多点互联、路由自学习、链路选优、故障快速收敛。覆盖全球 30+ 地域，支持 100+Gbps 带宽、最高 99.99% 可用性。

- 组成：关联网络实例（VPC / 专线网关 / VPN 网关）+ 自动学习的路由表。
- 加入同一云联网的实例即互通，无需逐条配路由。

### 与 VPC 对等连接（Peering）的区别

| 维度   | 对等连接 Peering                               | 云联网 CCN                       |
| ---- | ------------------------------------------ | ----------------------------- |
| 拓扑   | **两两互联**，n 个 VPC 需 `n*(n-1)/2` 条（4 个要 6 条） | 一个实例加多个 VPC，**全网自动互联**        |
| 路由   | 建连接后还需**手动配路由表**                           | **路由自动学习下发**，一次关联即可           |
| 跨地域  | 对等连接**已停服跨地域**（需用云联网）                      | 原生支持跨地域、跨账号                   |
| 网段限制 | 各 VPC 网段**不能重叠**，否则建不了                     | 也要求网段不重叠（CIDR 包含冲突时后关联者路由失效）  |
| 适用   | 少量、同地域 VPC 互通（免费）                          | 多 VPC / 跨地域 / 跨账号 / 含 IDC 的大网 |

> 本质：对等连接是「点对点手工拉线」，云联网是「把多条线插到一个智能交换机上，自动通」。

### 关联

- 见 Q16：用云联网打通多 VPC 的具体步骤。
- 见 Q17：CEN 属网络互联层，和 CLB/NAT/网关的流量入口定位不同。

## Q16（2026-08-06）：如何通过 CEN 实现多个 VPC 之间的互联互通？

> 控制台步骤（云联网 CCN）。

### 操作步骤

1. **新建云联网实例**：云联网控制台 →「新建云联网」→ 名称、计费模式（按带宽包/按流量计费）、服务质量（金/银/铜）。
2. **关联网络实例**：把要互通的 VPC 逐个「关联」到该云联网（选地域、VPC、子网）。如需连本地 IDC，也在此关联**专线网关 / VPN 网关**（一条物理专线只需一个专用通道 + 一个专线网关）。
3. **路由自动学习**：关联后云联网**自动学习**各 VPC 路由并下发到云联网路由表。到「路由表」确认互通路由已出现（无需手动加路由）。
4. **（可选）带宽管理**：跨地域/跨境配置带宽上限（绑定带宽包），避免某条链路占满。
5. **验证**：在 VPC-A 的 CVM 上 `ping` VPC-B 的 CVM **内网 IP**，通即互通成功。

### 注意事项

- **网段不能重叠**：多个 VPC 的 CIDR 若有包含关系，先关联的实例路由有效、后关联的冲突（CIDR 冲突原则）。
- **跨境需资质**：若涉及跨境（如国内↔海外），需先通过联通跨境资质审核，跨境带宽费用由联通收取。
- **跨账号**：跨账号关联需对方授权，且涉及网络连接实例费及入方向流量费。

### 排障/对照（**必会/可选**）

```bash
# 在 CVM 上验证跨 VPC 互通（内网 IP）
ping <对端VPC的CVM内网IP>
# 查看本机路由，确认去往对端网段的下一跳
ip route
```

> 不通先查：两 VPC 是否都关联到同一云联网、网段是否重叠、路由表是否学到对端路由、安全组是否放通。

### 关联

- 见 Q15：云联网 vs 对等连接的本质差异。
- 见 Q13：VPC 出公网走 NAT，跨 VPC 内网互通走云联网。

## Q17（2026-08-06）：CLB、NAT 网关、云原生网关这三者在流量入口场景下如何选型？

### 三者定位一览

| 组件         | 层          | 解决什么                 | 方向            | 典型角色                     |
| ---------- | ---------- | -------------------- | ------------- | ------------------------ |
| **CLB**    | L4 / L7 网络 | 流量接入 + 负载均衡 + 健康探测   | 入站为主          | 对外服务统一入口、分摊流量            |
| **云原生网关**  | 应用层（L7+）   | API 治理（限流/鉴权/灰度/可观测） | 入站（常位于 CLB 后） | 微服务/API 业务入口             |
| **NAT 网关** | L3/L4 地址转换 | 安全出公网（SNAT）          | **出站**为主      | 后端 CVM 访问 Internet，非对外入口 |

### 选型决策

- **需要对外提供高可用服务、分摊流量** → 必用 **CLB**（四层/七层按 Q12 选）。
- **除了转发，还要限流、鉴权、灰度、API 管理、链路追踪** → 在 CLB 之后加 **云原生网关**（微服务/API 场景）。纯静态/简单转发用 CLB 即可，不必上网关。
- **让无公网 IP 的后端访问公网（拉更新/调第三方）** → 用 **NAT 网关**（出站，不是入口）。
- **多 VPC / 跨地域内网互通** → 用 **云联网 CEN**（见 Q15/Q16），与三者入口定位不同。

### 推荐架构组合

```
外部请求 → [CLB]（四层/七层接入、负载均衡）
                ↓
         [云原生网关]（限流/鉴权/灰度/可观测，可选）
                ↓
         后端 TKE 服务 / CVM
后端服务出网 → [NAT 网关 SNAT] → 公网
```

- 简单场景可省去云原生网关：`外部 → CLB → 后端`，出网仍走 NAT。
- 三者不互斥：CLB 管接入、云原生网关管业务、NAT 管出网，各司其职。

### 关联

- 见 Q9/Q11：云原生网关的能力与插件。
- 见 Q12：CLB 四层/七层选型。
- 见 Q13/Q14：NAT 的定位与 CLB+NAT 组合。
- 见 Q5/Q6/Q10：这些入口最终都指向 TKE 内的 Service / 工作负载。

## Q18（2026-08-06）：腾讯云云防火墙 CFW 是什么？它防护的是什么层面的安全？

### 一句话理解

**云防火墙（Cloud Firewall, CFW）** 是腾讯云基于公有云的 **SaaS 化网络防火墙**，是整个云上网络的「统一访问控制中心」——在**网络层**做边界访问控制 + 入侵防御（IPS），覆盖**南北向（公网↔云）**&#x548C;**东西向（VPC 内/间）**&#x6D41;量，是业务的**第一道网络安全防线**。

### 防护层面（核心）

| 边界         | 防护什么                                   | 形态                |
| ---------- | -------------------------------------- | ----------------- |
| **互联网边界**  | 公网 IP 粒度的南北向流量：拦截入向攻击、管控出向外联（失陷主机非法外连） | 开关按公网 IP 开启       |
| **NAT 边界** | 子网出公网的流量过滤（类似 NAT 网关 + 防火墙），出向白名单管控    | 虚拟防火墙，自动改子网路由牵引流量 |
| **VPC 边界** | VPC 间/子网间的**东西向微隔离**，防单点被突破后的内网横向漫游    | 自动生成两两 VPC 子防火墙   |
| **企业安全组**  | 在原有安全组之上叠加五元组策略，万台资产一键下发、优先级更高         | 统一 ACL 平面         |
|            |                                        |                   |

### 核心能力

- **五元组访问控制**：按「源/目的 IP、端口、协议 + 域名/地域/标签」精细管控。
- **入侵防御（IPS）**：内置规则库（TCP/HTTP 协议规则、350+ 虚拟补丁），秒级更新威胁情报，拦截扫描探测、SQL 注入、挖矿、勒索、僵尸网络等 8 大类失陷行为。
- **资产与暴露面管理**：一键梳理公网/内网资产、端口、漏洞、Web 组件暴露面。
- **全流量分析（NDR）+ 日志审计**：满足等保 2.0 日志留存（≥6 个月）。
- **零信任接入**：运维端口（SSH/RDP）微信扫码认证，防暴力破解。

> 本质：**CFW 管「谁能访问、什么流量能进出网络」**，是网络层/边界层防护，不解析 Web 应用语义（那是 WAF 的活，见 Q19/Q20）。

### 关联

- 见 Q19/Q20：CFW（网络层）与 WAF（应用层）的分工。
- 见 Q13：NAT 边界防火墙原理类似 NAT 网关 + 安全审计。
- 见 Q22：CFW 是纵深防御的「边界」一层。

## Q19（2026-08-06）：WAF（Web应用防火墙）是什么？它能防御哪些常见的 Web 攻击？

### 一句话理解

**Web 应用防火墙（Web Application Firewall, WAF）** 是腾讯云基于 **AI + 规则双引擎**的 Web 业务安全防护产品，部署在 **应用层（HTTP/HTTPS）**，把恶意 Web 流量清洗掉、正常流量回源，专门挡**针对网站/Web 应用的攻击**。

### 能防御的攻击（按 OWASP Top 10 等）

| 类别        | 具体攻击                                   |
| --------- | -------------------------------------- |
| **注入类**   | SQL 注入、命令注入、代码注入、非授权访问                 |
| **脚本/跨站** | XSS（跨站脚本）、CSRF（跨站请求伪造）                 |
| **恶意代码**  | Webshell 木马上传、网页挂马、后门                  |
| **资源滥用**  | CC 攻击（频率/人机识别）、恶意爬虫 Bot、垃圾流量           |
| **漏洞应急**  | **0day 虚拟补丁**（高危 Web 漏洞 24h 内下发，无需改代码） |
| **篡改/泄漏** | 网页防篡改（云端替身缓存）、数据防泄漏（隐藏后端、替换敏感数据）       |

### 两种接入模式

- **SaaS 型 WAF**：DNS 把域名 CNAME 到 WAF 集群，源站 IP 配在 WAF 里，清洗后回源。需配合安全组防绕过（封源站直连）。
- **云原生型 WAF**：与**腾讯云 CLB**联动，把 CLB 的 HTTP/HTTPS 流量**旁路镜像**到 WAF 检测，清洗结果同步给 CLB 放行/拦截，转发与安全解耦（见 Q12/Q17）。

> 本质：**WAF 管「Web 请求里有没有攻击内容」**，只防护 HTTP/HTTPS 流量，是应用层防护（对应 CFW 不解析 Web 语义）。

### 关联

- 见 Q18/Q20：WAF 与 CFW 的层面分工。
- 见 Q23：Web 应用同时上 CFW + WAF 的链路。
- 见 Q12：云原生 WAF 与 CLB 七层监听器联动。

## Q20（2026-08-06）：CFW 和 WAF 有什么区别？各自在什么场景下使用？

### 核心区别

| 维度    | 云防火墙 CFW                   | Web 应用防火墙 WAF                     |
| ----- | -------------------------- | --------------------------------- |
| 防护层面  | **网络层（L3/L4）+ 入侵防御**       | **应用层（L7 HTTP/HTTPS）**            |
| 解析内容  | 五元组/端口/协议，**不解析 Web 业务语义** | 解析 HTTP 请求**内容**（参数、Body、Header）  |
| 防护对象  | **所有流量**（Web、数据库、SSH、任意端口） | **仅 Web 流量**（网站/API 的 HTTP/HTTPS） |
| 拦截的威胁 | 端口扫描、非法 IP、失陷外连、网络层入侵      | SQL 注入、XSS、Webshell、CC、Bot        |
| 典型角色  | 网络边界「谁能进出」                 | Web 应用「请求里有没有攻击」                  |

### 使用场景

- **用 CFW**：需要统一管控网络边界——公网 IP 访问控制、阻断恶意 IP、东西向微隔离、出向外联管控、满足等保边界防护。
- **用 WAF**：对外提供网站/API 服务，需要防 SQL 注入/XSS/CC/爬虫、防 Web 应用层攻击、0day 应急。
- **二者关系**：**互补、不冲突**。CFW 在网络层先过滤一遍（恶意 IP/端口/IPS），WAF 在应用层再过滤 Web 攻击。生产 Web 架构通常「CFW + WAF」双保险（见 Q22/Q23）。

### 关联

- 见 Q18/Q19：两者各自能力详解。
- 见 Q22：作为纵深防御的「边界 + 应用」两层。

## Q21（2026-08-06）：主机安全是什么？它能检测哪些风险（如漏洞、暴力破解、木马）？

### 一句话理解

**主机安全（Cloud Workload Protection, CWP，也称 CWPP）** 是腾讯云基于海量威胁情报 + 机器学习的**主机入侵检测与防护**产品。在 CVM/容器上装**客户端 Agent**，把风险上报云端分析，解决「服务器被入侵」的核心风险。支持腾讯云服务器 + 非腾讯云（混合云）。

### 能检测/防护的风险

| 类别        | 具体能力                                                 |
| --------- | ---------------------------------------------------- |
| **漏洞检测**  | 系统组件漏洞、Web 应用漏洞、应急漏洞；实时预警 + 修复建议（4w+ 漏洞库，0day 小时级更新） |
| **暴力破解**  | 检测 SSH/RDP 等密码破解尝试并**阻断**，异常登录（异地/非常用 IP/时间）告警       |
| **木马/病毒** | Webshell 检测、TAV/BinaryAI/云查杀引擎查杀挖矿、勒索木马，一键隔离         |
| **入侵行为**  | 反弹 Shell、本地提权、恶意请求、高危命令执行、核心文件监控                     |
| **安全基线**  | CIS / 等保二三级 / 腾讯最佳实践基线检测（弱口令、配置风险）                   |
| **资产指纹**  | 自动清点账号、端口、进程、组件，可视化暴露面                               |
| **攻击溯源**  | Cyber-Holmes 引擎自动还原完整攻击链路，日志留存可取证                    |

### 工作原理

安装 Agent 的服务器 → 客户端执行检测/处置任务并回传 → 主机安全云端（六大引擎：TAV、BinaryAI、云查杀、威胁情报、攻击防御、异常行为）判断 → 控制台统一查看处置。

### 关联

- 见 Q22：主机安全是纵深防御的「主机」一层。
- 见 Q24：与云堡垒机分工不同（主机状态 vs 运维行为）。

## Q22（2026-08-06）：CFW、WAF、主机安全如何协同工作，构建「纵深防御」体系？

### 纵深防御（Defense in Depth）三层模型

把攻击链条按「网络边界 → 应用层 → 主机」分层设防，**任一层被绕过，下一层仍能挡**：

```
公网攻击者
   │
   ▼ [第 1 层 · 网络边界] 云防火墙 CFW
   │   南北向访问控制、IPS 拦截扫描/入侵、东西向微隔离
   │   （挡掉大部分网络层乱序流量、恶意 IP、内网横移）
   ▼ [第 2 层 · 应用层] WAF
   │   SQL 注入 / XSS / Webshell / CC / Bot 拦截
   │   （Web 应用层攻击被清洗）
   ▼ [第 3 层 · 主机层] 主机安全 CWP
       漏洞/暴力破解/木马/提权/反弹Shell 检测与阻断
       （万一前两层漏过，主机端仍能发现并处置）
   后端 CVM / TKE 工作负载
```

### 协同要点（等保三级「铁三角」）

- **CFW 满足**：安全区域边界（边界防护、访问控制）、安全通信网络（网络架构可视）。
- **WAF 满足**：安全区域边界（入侵防范、恶意代码防范）、Web 应用层访问控制、安全审计。
- **CWP 满足**：安全计算环境（入侵防范、漏洞/基线管理）、主机层审计。
- **联动价值**：CFW 发现失陷主机外联 → 结合 CWP 定位木马；WAF 拦 Web 攻击 → CWP 防 WebShell 落地；三层日志统一进安全运营中心，可联动响应。

### 关联

- 见 Q18/Q19/Q21：三层各自能力。
- 见 Q23：Web 应用把第 1、2 层（CFW+WAF）落地配置。

## Q23（2026-08-06）：如何为一个 Web 应用同时配置 CFW 和 WAF？配置顺序和策略优先级是怎样的？

### 推荐链路（两层都上）

```
公网用户
   │
   ▼ [云防火墙 CFW · 互联网边界]（IP/端口/IPS 网络层过滤）
   │
   ▼ [WAF]（Web 应用层攻击清洗）
   │      ├─ SaaS 型：域名 CNAME → WAF → 回源 CLB/CVM
   │      └─ 云原生型：CLB 旁路镜像流量给 WAF 检测
   ▼ 源站（CLB → 后端 TKE/CVM）
```

### 配置顺序（控制台）

1. **先开 CFW（互联网边界）**：云防火墙控制台 → 开启对应公网 IP 的「防火墙开关」→ 配访问控制规则（默认拒绝、按需放行）+ 入侵防御（拦截/观察模式）。
2. **再接入 WAF**：
   - **SaaS 型**：WAF 控制台「添加域名」→ 填源站 IP → 把网站 DNS 解析改为 WAF 提供的 CNAME（此时流量先过 CFW 再过 WAF）。
   - **云原生型**：确认 CLB 已配好 → WAF「添加域名并绑定 CLB」→ 旁路检测自动生效（见 Q12/Q17）。
3. **防绕过**：源站只收 CFW/WAF 回源 IP，安全组封掉源站公网直连（或 CFW 已挡在边界）。
4. **验证**：从公网发正常请求 + 模拟攻击（如 `?id=1' or '1'='1`）→ CFW/WAF 控制台看拦截日志。

### 策略优先级（谁先生效）

- **CFW 在更外层（网络层）**：先按 IP/端口/IPS 过滤，**恶意 IP、非法端口、网络层入侵先被 CFW 挡掉**，根本到不了 WAF。
- **WAF 在应用层**：只处理到达的 HTTP/HTTPS 流量，做 Web 语义级清洗。
- 二者**互补无冲突**：CFW 不认识 SQL 注入、WAF 不认识端口扫描，各管一层。优先级本质是「**网络层 CFW 先、应用层 WAF 后**」的漏斗式过滤。

### 关联

- 见 Q18/Q19/Q20：CFW 与 WAF 能力及区别。
- 见 Q22：两层协同属纵深防御的边界 + 应用层。

## Q24（2026-08-06）：云堡垒机是什么？它和主机安全有什么不同？

### 一句话理解

**云堡垒机（Bastion Host, BH）** 是集 **4A（Account 账号 / Authentication 认证 / Authorization 授权 / Audit 审计）** 于一体的**集中运维管理系统**，作为所有运维操作的**统一入口 + 操作审计**平台，解决「谁、以什么权限、对哪台机器、做了什么操作」的管控与追溯问题。

### 云堡垒机 vs 主机安全的本质区别

| 维度   | 云堡垒机 BH                         | 主机安全 CWP                  |
| ---- | ------------------------------- | ------------------------- |
| 防护对象 | **「人」——运维人员/第三方**               | **「机器」——主机/容器**           |
| 关注点  | 运维**行为**：访问权限、操作命令、文件传输、是否越权    | 主机**状态**：有无漏洞、木马、被入侵、基线合规 |
| 工作位置 | 运维流量的**正向代理入口**（SSH/RDP 等先过堡垒机） | 主机上的 **Agent** 做检测/处置     |
| 核心价值 | 事前授权、事中监控、**事后审计溯源**、防内部泄密      | 入侵检测与防护、漏洞/基线管理           |
| 等保条款 | 满足「安全审计 / 身份鉴别 / 访问控制」（运维审计）    | 满足「安全计算环境」（入侵防范、漏洞管理）     |

> 一句话：**堡垒机管「运维的人干没干坏事」，主机安全管「主机本身有没有中招」**。两者互补——堡垒机看到谁登了机器、敲了什么命令；主机安全看到机器里有没有木马/异常。

### 关联

- 见 Q21：主机安全防护主机状态，与堡垒机的运维审计互补。
- 见 Q25/Q26：堡垒机怎么管多台 CVM、支持哪些协议和策略。

## Q25（2026-08-06）：如何使用云堡垒机来管理多台 CVM 的访问权限和操作审计？

> 控制台步骤（云堡垒机 BH）。目标是让**所有运维走堡垒机**，关闭服务器直连 SSH/RDP。

### 控制台操作步骤

1. **购买并创建堡垒机实例**：堡垒机控制台 → 新建实例（按云服务器数量选规格）→ 等待「运行中」。
2. **添加资产**：「资产管理」→ 添加 CVM（IP、协议如 SSH/RDP、托管资产账号密码）。堡垒机托管账号后，运维人员**无需记忆各机器密码**，只用自己堡垒机账号即可单点登录（SSO）。
3. **创建用户/用户组**：「用户管理」→ 建运维人员账号，可分组（如「开发组」「运维组」）。
4. **授权（最小权限）**：「授权管理」→ 配置「用户/用户组 → 资产 → 资产账号 → 操作权限（如只读/可写）」，按岗位给最小权限，禁止越权。
5. **运维人员登录运维**：运维人员登录堡垒机 Web 控制台 → 选目标资产 → 单点登录进 CVM，**所有命令/文件传输/会话被全程录制审计**。
6. **关闭直连端口**：在 CVM 安全组**关闭 22(SSH)/3389(RDP) 公网直连**，只留堡垒机入口，避免绕过审计直连服务器。
7. **审计与告警**：「审计中心」回放会话录像、检索命令/文件操作；对异常命令、异常 IP、批量下载等配置告警。

### 排障/对照（**必会/可选**）

```bash
# 验证运维是否只能经堡垒机：在 CVM 安全组确认 22/3389 仅对堡垒机 IP 放通
# 在堡垒机「会话审计」查看某次运维的录像与命令流水
```

> 若还能直连 CVM：检查安全组是否真关了直连端口；堡垒机未生效通常是资产账号托管或授权未配好。

### 关联

- 见 Q24：堡垒机与主机安全的分工。

## Q27（2026-08-06）：TDSQL-C MySQL 版是什么？和传统自建 MySQL 相比有什么核心优势？

**TDSQL-C MySQL 版** 是腾讯云自研的**新一代云原生关系型数据库**，**100% 兼容 MySQL 5.7 / 8.0**（应用几乎零改造迁移）。核心特征是「计算与存储分离 + 日志即数据库」，单节点百万级 QPS、最高 PB 级存储、秒级升配与故障恢复、Serverless 弹性。

| 扩缩容        | **秒级**升配、加只读节点；磁盘扩容业务无感知                           | 升级规格/加从库需搬迁数据，小时～天级   |

## Q28（2026-08-06）：TDSQL-C 的「计算与存储分离」架构是什么意思？它如何提升性能？

### 架构含义（计算与存储分离 + 日志即数据库）

- **计算层（无状态）**：多个计算节点（1 读写 + N 只读）**共享同一份底层存储**，只负责 SQL 解析与执行，不持久化数据页——节点宕机/扩容只需启新进程，**秒级完成**。
- **存储层（池化）**：构建在腾讯云分布式云存储之上，负责持久化日志、回放日志、生成数据页面，单实例可达 PB 级。
- **日志即数据库（Log is Database）**：写入时计算节点**只传物理日志（redo log）**&#x7ED9;存储层，不写数据页；存储层持久化日志→回放生成页面。相比传统「写 redo + binlog + 数据页」，整体 IO 减少 **60%+**。

### 写入流程

```
计算节点(W) → 仅传 redo log → 存储层
   存储层：① 持久化日志 → ② 通知客户端(ACK) → ③ 回放日志 → ④ 生成数据页 → ⑤ 回收旧日志
```

备库（只读节点）直接**内存回放 redo**生成数据页、无需落盘，因此主备延迟降到 ms 级。

### 如何提升性能

| 机制                      | 性能收益                     |
| ----------------------- | ------------------------ |
| 只写 redo，去掉 binlog/数据页双写 | 写 IO 减 60%+，写入性能 +140%   |
| 计算节点无状态                 | 秒级升配/故障切换（物理机宕机 1 分钟内恢复） |
| 存储池化 + SPDK/RDMA 零拷贝    | 减少上下文切换与拷贝，降低延迟          |
| 备库内存回放                  | 主从延迟 ms 级，读扩展近乎线性        |
| 快照备份 + 并行回档             | GB/秒级回档，备份不阻塞业务          |

- 见 Q27：存算分离带来的核心优势对比
- 见 Q29/Q30：引擎与只读实例都建立在存算分离之上。

## Q29（2026-08-06）：TDSQL-C 支持哪些引擎？InnoDB 和 RocksDB 分别适用什么场景？

### 支持的引擎

TDSQL-C MySQL 版提供多引擎，适配不同负载：

| 引擎                          | 适用场景                                             |
| --------------------------- | ------------------------------------------------ |
| **InnoDB**（默认）              | 通用 OLTP 事务型负载；高并发读写、强一致、写 QPS 要求高（订单、交易、金融）      |
| **LibraDB**（腾讯自研列存/HTAP 引擎） | 复杂分析查询、实时数据分析、多维读取；列存索引 + 并行查询，分析性能可提升 10 倍      |
| **RocksDB**                 | 写密集、大容量、对存储成本敏感的 KV/日志类场景；LSM 树顺序写、高压缩比，适合海量历史数据 |

### InnoDB vs RocksDB 怎么选

| 维度   | InnoDB             | RocksDB               |
| ---- | ------------------ | --------------------- |
| 数据结构 | B+ 树，随机读写友好        | LSM 树，顺序写、高压缩         |
| 擅长   | 事务、点查、高并发读写、低延迟    | 海量写入、大容量存储、成本敏感       |
| 典型场景 | 核心交易/订单、用户中心       | 历史流水、日志归档、IoT 时序写、冷数据 |
| 选它当  | 需要强一致事务 + 高 QPS 读写 | 写远大于读、数据量极大、要省存储成本    |

> 经验：**绝大多数业务用默认 InnoDB**；只有当数据量巨大、写多读少、对存储成本敏感时再考虑 RocksDB；需要 OLAP 分析叠加时看 LibraDB（HTAP）。引擎在创建实例时选定，注意不同引擎支持的版本/规格差异（以控制台可见为准）。

## Q30（2026-08-06）：TDSQL-C 的只读实例和读写分离怎么配置？

### 概念

- **只读实例（RO）**：一个 TDSQL-C 集群含 **1 个读写实例（主）+ 最多 15 个只读实例**。只读实例共享主库存储、基于 redo 低延迟同步，用于分担读压力（千万级读 QPS）。
- **读写分离**：通过**数据库代理（Proxy）** 统一接入地址，自动把写请求路由到读写实例、读请求按权重分发到只读实例，应用只需连一个地址。

  ### 控制台配置步骤						

1. **加只读实例**：集群列表 → 目标集群 →「管理」→「只读实例」→「新建」→ 选规格/节点，秒级添加（共享存储、无需迁数据）。
2. **开启数据库代理（读写分离）**：集群详情 →「数据库代理」→「开启」→ 配置代理规格。
3. **设置读写分离策略**：在代理里配置**读权重**（读写实例 vs 各只读实例的流量比例）、**读请求分发**（如「只读实例均摊 / 按权重」）、以及「**是否延迟剔除**」（只读延迟超阈值自动摘除，避免读脏数据）。
4. **连接代理地址**：应用把连接串从原读写地址改为**代理地址**，无需改业务代码即实现读写分离。
5. **（可选）只读组**：把多个只读实例加入只读组，统一管理与权重。

### 注意事项

- 读写分离**只对读请求生效**，写永远走主实例；事务内的读默认也走主（避免不可重复读），具体看代理的「事务内读」策略。
- 只读实例延迟要监控（见 Q32 告警），延迟过高时读分离可能返回旧数据。
- 若不使用代理、手动在代码里区分读写数据源，则无需代理，但需自管连接与权重。

### 排障/对照（**必会/可选**）

```bash
# 查看只读实例延迟（主从差距），单位秒
# 在可观测平台/TDSQL-C 控制台看「只读实例延迟」指标，或用 SQL：
SHOW SLAVE STATUS\G     # 看 Seconds_Behind_Master（传统视角）
```

> 若读分离没生效：检查应用是否连的是代理地址、读权重是否配置、事务内读是否被强制走主。

### 关联

- 见 Q28：只读实例共享存储、redo 低延迟同步的基础。
- 见 Q29：只读实例可按引擎（如 LibraDB）分担分析读。
- 见 Q32：为只读延迟配告警。

## Q32（2026-08-06）：如何为 TKE 集群或 TDSQL-C 设置告警策略？告警规则怎么配置？

> 控制台步骤（可观测平台 → 告警管理 → 告警配置）。

### 告警策略的 5 个必要要素

**策略名称、监控类型、策略类型、告警对象、触发条件（+ 告警通知）**。

### 通用配置步骤

1. 进入**可观测平台控制台** →「告警管理」→「告警配置」→「告警策略」→「新建策略」。

5. **触发条件**（核心）：由「指标 + 比较关系 + 阈值 + 统计粒度 + 持续 N 个数据点」组成。例如：CPU 利用率 `>` 80%，统计粒度 5 分钟，持续 2 个周期 → 触发。

6. **告警通知**：选通知模板（系统预设或自定义，最多绑 3 个），渠道含短信/邮件/站内信/回调 URL。
7. **（可选）弹性伸缩**：部分产品可授权告警触发弹性伸缩。
8. 保存即生效。

| **TDSQL-C** | CPU/内存利用率、连接数、QPS、慢查询数、**只读实例延迟（主从延迟）**、存储使用率、备份失败               |

### 一、产品选型清单（各产品解决什么）

### 二、端到端数据流（一次访问的完整路径）

```
开发者 git push
    │
    ▼  CNB 流水线（.cnb.yml）
    │    Maven 编译 → 单元测试 → 打镜像 → 推 CNB 制品库(docker.cnb.cool)
    ▼  CNB 部署 TKE（deploy-to-tke 插件 / kubectl apply）
    │    滚动更新 TKE 工作负载，新镜像从 CNB 制品库拉取
    │
公网用户 ──HTTP(S)──┐
                    ▼  [CFW 互联网边界]（IP/端口/IPS 网络层过滤）★最外层
                    ▼  [WAF]（Web 攻击清洗）★应用层
                    ▼  [CLB]（公网 LB，可选）
                    ▼  [云原生网关 TSE]（限流/鉴权/灰度/路由到 Service）
                    ▼  TKE Service → Pod（应用容器）
                    ▼  [TDSQL-C]（经数据库代理读写分离，只读走只读实例）
后端出网 ──────────▶  [NAT 网关 SNAT] → 公网
全程监控/审计：TCOP（指标/告警/Dashboard） + 主机安全 CWP + 堡垒机 BH
```

### 三、落地要点

1. **构建**：CNB 控制台建仓库 → 根目录放 `.cnb.yml`（见 Q2 模板）→ 提交即触发。镜像推 `docker.cnb.cool`，凭据走 CNB Secret 仓库，**不写明文**。
2. **部署**：优先用 **`deploy-to-tke` 插件**（参数化、免 kubectl，见 Q3）；TKE 拉 CNB 制品库私有镜像需配 `imagePullSecret`（见 Q3 备注）。排障才用 kubectl。
3. **入口**：TSE 控制台新建网关 → 服务来源选「Kubernetes(TKE)」自动发现 Service → 建路由（域名/路径→后端 Service）。要限流/灰度就在网关上绑插件（见 Q11）。
4. **安全**：先开 **CFW** 互联网边界（IP/端口/IPS），再接 **WAF**（SaaS 型改 DNS CNAME 或云原生型绑 CLB，见 Q23）。源站安全组封公网直连防绕过。
5. **数据**：TDSQL-C 控制台建实例（InnoDB 默认）→ 开数据库代理做读写分离 → 应用连代理地址（见 Q30）。
6. **可观测**：TCOP 给 TKE/DB 配告警（节点 NotReady、Pod 重启、只读延迟等，见 Q32）+ 建 Dashboard（见 Q33）；TKE 深度监控用 TMP + TCMG（见 Q31）。
7. **运维**：所有到 CVM/TKE 节点的操作经**云堡垒机**（见 Q25），节点装**主机安全 Agent**（见 Q21）。

> 这是一个「纵深防御 + 全托管 + 可观测」的标准 Web 应用底座。按实际规模裁剪：小项目可省云原生网关（CLB 直连 TKE）、省只读实例；但 CFW+WAF 双保险、TCOP 监控建议常驻。

## Q35（2026-08-06）：典型三层架构（Web/应用/数据库）在腾讯云的产品选型与网络/安全设计

> 把 Q34 的方案按「Web 层 / 应用层 / 数据库层」经典分层重新组织，专讲每层选什么、网络怎么划、安全怎么设。

### 一、三层 → 腾讯云产品映射

| 架构层              | 职责                  | 推荐产品                                                | 说明                                        |
| ---------------- | ------------------- | --------------------------------------------------- | ----------------------------------------- |
| **Web 层（接入/展示）** | 接收公网请求、TLS 终止、静态/转发 | CLB（L4/L7）+ 云原生网关 TSE（可选）+ WAF + CFW                | 对外唯一入口；纯转发用 CLB，要 API 治理加网关（见 Q9/Q12/Q17） |
| **应用层（业务逻辑）**    | 业务逻辑、会话、调用下游        | **TKE**（Deployment/StatefulSet + Service）+ CNB 构建部署 | 无状态业务跑容器，弹性靠节点池+HPA（见 Q4/Q5/Q7）           |
| **数据库层（持久化）**    | 结构化数据存储             | **TDSQL-C MySQL**（InnoDB 默认，代理读写分离 + 只读实例）          | 存算分离、秒级扩只读（见 Q27/Q30）                     |
| **横向能力**         | 出网/监控/运维            | NAT 网关、可观测平台 TCOP、云堡垒机 BH、主机安全 CWP                  | 贯穿三层（见 Q13/Q14、Q31、Q24/Q21）               |

### 二、网络设计（VPC 子网分层 + 安全隔离）

建议把三层放在**同一 VPC 的不同子网**（或按合规要求跨 VPC 用云联网 CEN 打通，见 Q15/Q16），通过安全组 + 路由做隔离：

```
VPC（如 10.0.0.0/16）
 ├─ 公网接入子网（Web 层）
 │     CLB（公网）、云原生网关、WAF 回源、NAT 网关
 │     安全组：仅放通 80/443 入站；CFW 互联网边界管控
 ├─ 应用子网（应用层）
 │     TKE 节点（VPC-CNI，Pod 拿 VPC IP）
 │     安全组：仅接受来自 Web 子网 CLB/网关的流量；出网默认 0.0.0.0/0 → NAT
 └─ 数据子网（数据库层）
       TDSQL-C（私有网络，不绑公网）
       安全组：仅接受来自应用子网 TKE Pod/节点 IP 的 3306 入站
```

- **入站**：公网 → CFW → WAF → CLB/网关 → 应用子网 TKE → 数据子网 DB。
- **出站**：应用/数据子网默认路由指向 **NAT 网关**出公网（拉镜像/调三方 API），避免实例绑公网 IP（见 Q13/Q14）。
- **跨层可达**：用**安全组**控制「Web 子网可访应用子网、应用子网可访数据子网、反向默认拒绝」，实现东西向微隔离（CFW 企业安全组可统一下发，见 Q18）。

### 三、安全设计（纵深 + 等保）

| 层      | 安全手段                                   | 对应知识点       |
| ------ | -------------------------------------- | ----------- |
| 边界（最外） | **CFW** 互联网边界五元组 + IPS，挡恶意 IP/端口/入侵    | Q18、Q23     |
| 应用层    | **WAF** 清洗 Web 攻击；云原生网关做限流/鉴权/JWT      | Q19、Q20、Q11 |
| 主机层    | TKE 节点 + CVM 装**主机安全 CWP**（漏洞/暴力破解/木马） | Q21、Q22     |
| 数据安全   | DB 仅私网、最小权限账号、传输加密；**CFW 东西向**防内网横移    | Q18、Q27     |
| 运维审计   | 所有运维经**云堡垒机 BH**，关 22/3389 直连；操作全程审计   | Q24、Q25、Q26 |
| 可观测    | **TCOP** 全链路监控 + 告警 + Dashboard，异常早发现  | Q31、Q32、Q33 |

> 三层架构的本质是「**分层解耦 + 每层独立弹性 + 每层独立设防**」。Web 层无状态可多实例，应用层容器化弹性扩缩，数据库层靠只读实例分担读——配合网络分段与安全分层，就是腾讯云上的标准企业级落地形态。

### 关键链路说明（一句话串起来）

1. **开发→上线**：`git push` → CNB（.cnb.yml）→ 编译打镜像推 CNB 制品库 → `deploy-to-tke` 滚动更新 TKE 工作负载。

3. **出网**：后端经 NAT 网关安全出公网，无公网 IP。
4. **防护**：网络层(CFW)→应用层(WAF)→主机层(CWP) 纵深；运维经堡垒机审计。
5. **可观测**：TCOP 统一采集 TKE/DB/网络指标，配告警 + Dashboard，异常即时发现。
